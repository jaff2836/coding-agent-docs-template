# Review Round Protocol

이 문서는 사용자가 **리뷰 라운드를 명시적으로 시작한 경우에만** 적용합니다. 일반적인 PR·diff 리뷰 요청에는 [REVIEW.md](./REVIEW.md)만 적용하고 이 절차를 적용하지 않습니다.

예외적으로 이전 라운드의 세션 인계 목록을 넘겨받은 **다음 관련 구현·문서 수정 작업**에서는 §9의 문서 반영 절차만 적용합니다. 이것만으로 라운드를 다시 시작하거나 §1의 권한을 위임받지는 않습니다.

[REVIEW.md](./REVIEW.md)가 **무엇을 결함으로 판단하는가**를 정의한다면, 이 문서는 **그 결과를 받아 누가 언제 수정·commit·merge하는가**를 정의합니다.

## Metadata

- **Status:** Active
- **Owner:** 프로젝트에 맞게 작성
- **Last reviewed:** YYYY-MM-DD
- **Review cadence:** 라운드 정책 또는 권한 위임 범위 변경 시

## 1. 권한 위임

[AGENTS.md](../AGENTS.md)는 명시적인 요청 없는 commit, push, branch 삭제 및 배포를 금지합니다. 라운드 시작은 그 금지에 대한 **범위가 한정된 예외**입니다.

**위임되는 것** — 시작 시 확정하거나 이후 사용자가 명시적으로 변경한 파라미터 범위 안에서만:

- 유효한 finding에 대한 코드 수정
- 라운드별 commit
- 대상 branch로의 non-force push. 리뷰어가 push로 트리거되는 구성에서는 보통 push가 다음 라운드를 시작합니다. 라운드가 시작되는 조건 자체는 §3·§4가 정합니다(base 변경은 push 없이도 새 라운드입니다)
- `rereview = request`일 때, §2.1 표에 등록된 방법으로의 **재리뷰 요청** — 트리거 댓글 게시 또는 리뷰어 재요청 API 호출. 등록된 문구·호출을 그대로 사용하며 임의로 변형하지 않습니다
- §6에 따라 **처리한 finding의 인라인 스레드를 해소 표시**하는 것. 처리하지 않은 finding의 스레드는 닫지 않습니다
- 통과 시 **사용자 확인을 거친** merge

**위임되지 않는 것:**

- branch 삭제 (로컬·원격 모두)
- force push 및 history 재작성
- 대상 branch 밖의 파일 또는 branch 변경
- 재리뷰 요청 이외의 PR 댓글, 그리고 리뷰어에게 코드 수정을 지시하는 멘션. 일부 리뷰어는 트리거 문구 뒤에 다른 말이 붙으면 리뷰 대신 코드를 수정하는 태스크를 시작하고 branch에 push합니다. 그 push는 위임 범위 밖입니다
- 배포, 릴리스 게시, tag 생성, 마이그레이션 실행, 의존성 설치
- 라운드 수와 임계값의 임의 변경
- 사용자 확인 없는 merge

이 문서를 읽지 않은 실행에서는 [AGENTS.md](../AGENTS.md)의 기본 금지 규칙이 그대로 적용됩니다.

## 2. 파라미터

| 파라미터 | 기본값 | 설명 |
|---|---|---|
| `rounds` | `5` | 최대 라운드 수 |
| `threshold` | `모든 P0 = 0, 모든 P1 = 0, blocking P2 = 0` | 사용자가 변경할 수 있는 기본값입니다. 유효하고 미해소인 finding을 집계하며, 기본값에서는 모든 P0·P1과 [REVIEW.md](./REVIEW.md) §4.3 Blocking의 `blocking=true`인 P2를 사용합니다 |
| `target` | 현재 branch 또는 PR | 라운드 대상 |
| `reviewers` | §2.1의 상시 리뷰어 전체 | 결과를 기다릴 리뷰어. 등록 항목은 §2.1. `self`로 지정하면 등록 없이 실행 주체가 [REVIEW.md](./REVIEW.md)로 직접 리뷰합니다. 외부 리뷰 요청·대기와 §4의 정족수·타임아웃·head 정렬은 적용하지 않습니다. 원장 위치는 §7을 따릅니다 |
| `reviewer_timeout` | `45분` | 한 리뷰어의 결과를 기다리는 최대 시간 |
| `rereview` | `auto` | 라운드 안의 push 뒤 재리뷰를 어떻게 받는지. `auto`는 리뷰어 자체 트리거에만 의존합니다. `request`는 §2.1 표의 `재리뷰 요청 방법`이 등록된 리뷰어에게 실행 주체가 직접 요청합니다(§3). 사용자가 지정할 때만 `request`로 합니다 |
| `on_pass` | PR은 사용자 확인 후 merge, PR이 없으면 `merge 안 함` | `merge 안 함`이면 통과 결과와 인계 항목을 보고하고 종료합니다. 모든 모드의 저장소 문서 반영은 §9에 따라 다음 작업에서 수행합니다 |
| `close_branch` | 하지 않음 | 위임 대상이 아닙니다 |

**사용자 지정 임계값이 기본값보다 우선합니다.** 별도 지정이 없을 때만 표의 기본값을 사용합니다. 통과 판정, 수정 대상과 이관 대상은 모두 실제 확정한 `threshold`를 따릅니다. 예를 들어 사용자가 `모든 P0 = 0, 모든 P1 = 0`만 요구하면 P2는 `blocking=true`여도 이관할 수 있습니다. 반대로 모든 P2·P3까지 0개로 지정하면 그 항목도 해결해야 합니다. 중요도와 `blocking` 분류를 바꾸는 것과 임계값을 바꾸는 것은 별개입니다.

사용자가 진행 중 임계값을 명시적으로 변경하면 이전 값·새 값·적용 시점과 요청을 세션 원장에 남기고, 새 값을 되읽은 뒤 현재 finding을 재평가합니다. 실행 주체가 수렴을 위해 임의로 완화하지 않습니다. 임계값 변경 자체는 정족수·필수 검증·merge 권한을 변경하지 않습니다.

시작 전에 확정한 파라미터를 사용자에게 되읽어 주고 시작합니다. 되읽기 없이 라운드를 시작하지 않습니다. 외부 리뷰어를 사용하고 `rereview = auto`인데 §2.1의 상시 리뷰어 중 `재리뷰 요청 방법`이 `push 자동`인 리뷰어가 하나도 없으면, 2라운드부터 상시 리뷰어의 결과가 오지 않아 정족수를 채울 수 없다는 점을 되읽기에 포함하고 `request`로 바꿀지 묻습니다. 사용자가 `auto`를 유지하면 그대로 진행합니다. `reviewers = self`에서는 `rereview`·`reviewer_timeout`을 사용하지 않습니다. PR 없이 branch 간 merge를 수행하려면 대상 branch와 방식에 관한 별도 지시가 필요합니다.

PR 규모와 리뷰어 수에 따라 실제 필요한 라운드 수는 크게 달라집니다. `rounds`는 시작점일 뿐이며, 소진 시 §6에 따라 연장을 제안합니다.

기본 임계값은 [REVIEW.md](./REVIEW.md) §10 Review Conclusion의 verdict 규칙보다 엄격합니다. verdict는 blocking P0·P1에서만 `request_changes`가 되지만, 기본 라운드 임계값에서는 모든 P0·P1과 Blocking P2가 통과를 막습니다. `blocking`은 변경과 결함의 관계를 나타내는 값으로 유지하며, 통과를 막는다는 이유로 `false`를 `true`로 바꾸지 않습니다.

유효하고 미해소인 finding 하나가 기본 임계값에 미치는 영향은 다음과 같습니다. 무효이거나 현재 코드에서 해소가 확인된 finding은 집계하지 않습니다.

| 중요도 | `blocking=true` | `blocking=false` |
|---|---|---|
| P0 | 미통과 | 미통과 |
| P1 | 미통과 | 미통과 |
| P2 | 미통과 | 통과를 막지 않음 |
| P3 | 통과를 막지 않음 | 통과를 막지 않음 |

### 2.1 리뷰어 등록

이 표는 템플릿 적용 시 Maintainer가 작성합니다. 이 저장소에서 실제로 도는 리뷰어를 **전부** 조사해 기록합니다. 리뷰어를 누락하면 §4의 정족수 판정이 틀립니다. 라운드 실행 중에는 이 문서를 수정하지 않으며, 외부 리뷰어를 사용하는데 표가 비어 있으면 라운드를 시작하지 않고 등록을 요청합니다. `reviewers = self`는 이 표를 사용하지 않으므로 비어 있어도 시작합니다.

리뷰어는 **도착 주기**로 나뉩니다. 이 구분은 **기다릴지 여부만** 가르며 finding의 가치를 가르지 않습니다.

- **상시 리뷰어:** 변경마다 결과를 남깁니다. §4의 정족수 대상입니다.
- **간헐 리뷰어:** 일부 변경에만, 또는 PR당 한 번만 결과를 남깁니다. 정족수 대상이 아니며 도착한 라운드에서만 pool에 추가합니다. PR당 1회만 도는 리뷰어를 정족수에 넣으면 두 번째 라운드부터 영원히 채울 수 없습니다.

| 리뷰어 | 게시 위치 | head 식별 방법 | 도착 주기 | 문제가 없을 때 | 재리뷰 요청 방법 |
|---|---|---|---|---|---|

각 열에 기록할 내용입니다.

- **게시 위치:** PR 코멘트인지, PR review 본문인지, 인라인 스레드인지. **여러 곳에 나눠 쓰는 리뷰어는 그 전부를 적습니다.** PR 코멘트라면 head마다 새 코멘트를 남기는지, 코멘트 하나를 덮어쓰는지(sticky)도 적습니다. 덮어쓰는 리뷰어는 §7의 원장 규칙이 달라집니다
- **head 식별 방법:** 그 결과가 어느 커밋을 본 것인지 알아내는 방법. 마커 주석, 본문의 SHA, 라운드 번호 등
- **도착 주기:** 상시 또는 간헐. 간헐이면 어떤 조건에서 도는지
- **문제가 없을 때:** 결과를 남기는지 여부. §4의 타임아웃 처리가 이 값에 따라 달라집니다
- **재리뷰 요청 방법:** 새 push에 대해 리뷰를 다시 받는 방법. 다음 중 하나를 적습니다.
  - `push 자동` — push마다 스스로 다시 돕니다. 트리거 조건(ruleset, workflow 이벤트 등)을 함께 적습니다
  - 요청 방법 — 정확한 트리거 댓글 본문 또는 API 호출과, **요청이 접수되었는지 확인하는 방법**(반응 이모지, REST `requested_reviewers` 또는 GraphQL `reviewRequests`에 리뷰어가 포함되는지 등. 리뷰어가 실행을 시작하면 요청 목록에서 빠지는 경우가 있으므로 확인은 호출 직후에 합니다). 확인에 쓰는 식별자는 그 API의 필드 값을 그대로 씁니다. REST bot username에는 `[bot]`이 붙는 경우가 많고 GraphQL `Bot.login`에는 없는 경우가 많습니다. 서로 다른 API의 표기를 같은 문자열로 취급하지 않습니다. `rereview = request`일 때 실행 주체가 이 열을 그대로 실행합니다
  - `불가` — 재리뷰 수단이 없습니다. 이 리뷰어는 도착 주기가 간헐이어야 합니다

"PR당 1회"인 공개 리뷰어는 이 열이 비어 있으면 `rereview = request`로도 재리뷰를 받을 수 없습니다. 자동 리뷰가 켜져 있어도 대개 PR을 열 때 한 번만 돌고 push마다 돌지 않으므로, 도구 문서에서 재요청 방법을 확인해 적어 두세요.

## 3. 한 라운드의 4단계

```text
[1. 리뷰 대기] → [2. 리뷰 확인] → [3. 수정] → [4. commit]
```

**1. 리뷰 대기** — 리뷰를 요청하고 결과가 도착할 때까지 대상 코드를 동결합니다. 리뷰어마다 소요 시간이 다르므로 §4의 정족수 조건을 충족하거나 `reviewer_timeout`에 도달할 때까지 기다립니다. 요청 방식은 다음과 같습니다.

`reviewers = self`이면 외부 요청·대기 대신 현재 대상 변경을 [REVIEW.md](./REVIEW.md)에 따라 직접 리뷰한 뒤 2단계로 진행합니다. 아래 외부 리뷰 요청 분기는 적용하지 않습니다.

- **1라운드:** 대상 PR에 현재 head를 본 결과가 있는 리뷰어는 그것을 사용하며 다시 요청하지 않습니다. PR을 열 때 자동으로 도는 리뷰어는 이 시점에 이미 결과를 남긴 경우가 많습니다. `rereview = request`이면, 시작 시 확정한 `reviewers`에 들어 있고 §2.1에 댓글·API처럼 **명시적으로 실행할 요청 방법**이 있으며 현재 head 결과가 없는 리뷰어에게만, push가 없어도 그 방법을 실행하고 아래 `request`와 같이 접수 확인을 합니다. `push 자동`만 있는 리뷰어는 이 단계에서 요청하지 않습니다.
- **push가 있었던 라운드:** §2.1 표의 `재리뷰 요청 방법`이 `push 자동`인 리뷰어는 push 자체가 요청입니다. 그 외 리뷰어는 `rereview` 값에 따릅니다.
  - `auto` — 요청하지 않고 기다립니다. 결과가 오지 않으면 §4의 타임아웃 규칙을 적용합니다.
  - `request` — push 직후, 확정한 `reviewers`에 들어 있고 `push 자동`이 아닌 요청 방법이 있는 리뷰어에게만 표에 적힌 방법을 **그대로** 실행합니다. 트리거 댓글은 등록된 본문만 담고 다른 문장을 덧붙이지 않습니다. 표의 확인 방법으로 접수 여부를 확인합니다. 확인 신호가 요청 응답에 포함되는 방법(GraphQL `reviewRequests` 등)은 호출 직후 그 응답으로 판단합니다. 확인 신호가 요청과 별도로 도착하는 방법(댓글 반응 등)은 즉시 한 번만 보고 실패로 보지 말고, 신호가 나타나거나 접수 확인 한도(기본 2분, `reviewer_timeout`과 별개)에 이를 때까지 다시 확인합니다. 한도를 넘겨도 신호가 없으면 `reviewer_timeout`을 기다리지 않고 즉시 사용자에게 보고합니다. 일부 리뷰어의 재요청 API는 성공 응답을 돌려주면서 실제로는 아무 일도 하지 않으므로 응답 코드만으로 접수를 판단하지 마세요. **접수가 확인된 리뷰어는 그 라운드에 한해 §4의 정족수에 포함합니다** — 결과가 도착하거나 `reviewer_timeout`에 이를 때까지 기다립니다. 상시 리뷰어가 먼저 도착했다는 이유로 요청한 리뷰를 기다리지 않고 통과를 판정하면 이 모드를 쓰는 이유가 없어집니다.
- **push가 없었던 라운드:** 재리뷰를 요청하지 않습니다. 같은 head에 대한 두 번째 리뷰는 라운드가 아닙니다. 예외는 §4의 **base 변경**입니다. base가 바뀐 라운드는 head가 같아도 diff가 다르므로 push가 있었던 라운드와 같이 처리합니다 — `rereview = request`면 요청하고, `auto`면 기다립니다. `push 자동` 리뷰어의 트리거가 base 변경을 포함하지 않으면(retarget은 `synchronize`가 아니라 `edited`입니다) 결과가 오지 않으므로 §4의 타임아웃 규칙에 따라 `결과 없음`으로 기록하고 §6 확인 단계에서 명시합니다.

**2. 리뷰 확인** — 도착한 결과를 §4에 따라 통합하고, finding별로 유효·무효를 판정하고(§5), 임계값을 평가합니다. **통과 판정은 이 시점에 합니다.**

**3. 수정** — 유효하고 미해소인 finding 중 확정한 임계값을 충족하는 데 필요한 항목을 수정합니다. 기본값에서는 모든 P0·P1과 Blocking P2입니다. 그 밖의 finding을 함께 수정할 수 있으며, 그 수정은 다음 라운드에서 리뷰됩니다. 기본값에서는 기존 결함이나 이월 작업인 P0·P1도 통과를 막지만, 해결에 위임 범위를 넘는 변경이 필요하면 §8에 따라 중단하고 사용자 지시를 기다립니다.

**4. commit** — 위험에 비례해 [AGENTS.md](../AGENTS.md)의 Build, Test, Lint, Typecheck를 실행하고 결과를 기록합니다. 생성 파일이 있는 저장소는 재생성과 생성물 검사까지가 검증입니다. 과금이 발생하거나 외부 서비스를 호출하는 검증은 라운드 안에서 실행하지 않습니다. 라운드는 같은 검증을 여러 번 돌리므로 비용과 부작용이 누적됩니다. 검증이 실패하면 commit하지 않고 보고합니다. 커밋 메시지에 라운드 번호와 처리한 finding ID를 남깁니다.

## 4. 여러 리뷰어의 결과 통합

`reviewers = self`이면 이 절을 건너뛰고 §5로 진행합니다.

리뷰어를 여럿 두는 목적은 한 리뷰어가 놓친 것을 다른 리뷰어가 잡는 것입니다. 따라서 **finding은 전원의 것을 모두 모으고, 어느 것도 리뷰어를 이유로 버리지 않습니다.** finding의 무게에 리뷰어별 등급을 두지 않습니다. §2.1의 상시·간헐 구분은 **기다릴지 여부만** 가르며 finding의 가치를 가르지 않습니다.

**수집:** 도착한 모든 리뷰어의 finding을 하나의 pool로 모읍니다. **한 리뷰어의 결과는 여러 곳에 나뉘어 있습니다.** 최소한 다음을 모두 읽으세요.

- PR 코멘트 (봇의 sticky 코멘트 포함)
- PR review의 top-level 본문
- **줄에 붙은 인라인 리뷰 스레드** — 미해결·해결 모두
- 스레드의 후속 답글. 첫 코멘트만 읽으면 철회되거나 보강된 내용을 놓칩니다
- review 본문의 **접힌 `<details>` 블록**. 일부 리뷰어는 저신뢰 finding을 "Suppressed comments" 같은 접힌 블록에 넣습니다. 접혀 있다는 이유로 finding이 아닌 것은 아니며, §5에 따라 판정합니다

**top-level 요약이 그 리뷰어의 finding을 전부 담는다고 가정하지 마세요.** 요약이 "결함 없음"이나 `approve`인데 인라인에 차단 finding이 달려 있는 경우가 실제로 있습니다. 요약과 인라인이 다르면 인라인이 더 구체적인 근거를 가진 쪽입니다.

미해결 스레드 목록은 그 자체로 신호입니다. 라운드를 시작할 때와 통과를 판정할 때 각각 확인하세요.

**head 정렬:** 각 결과가 어느 head를 본 것인지 확인합니다. 현재 head와 다른 head를 본 결과는 이번 라운드의 판정 근거로 쓰지 않습니다. 단 head 표시가 없고 PR당 한 번만 도착하는 리뷰어는 예외이며, 그 finding이 현재 head에서 해소되었는지 코드로 직접 확인하고 근거를 남깁니다. 오래되었다는 이유만으로 버리지 마세요.

**base 변경:** PR의 base가 바뀐 경우 — 다른 branch로 retarget, base branch를 merge 또는 rebase, stacked PR의 아래 PR이 병합됨 — 리뷰어가 본 diff와 현재 diff가 다릅니다. head SHA가 같아 보여도 이전 결과는 판정 근거로 쓰지 않고 새 라운드로 셉니다. 실행 주체가 할 수 있는 base 변경은 base branch를 대상 branch에 **merge**하는 것뿐이며 §1의 non-force push 범위 안입니다. rebase는 force push를 요구하므로 위임되지 않고, retarget과 아래 PR의 병합은 라운드 밖에서 일어나는 변경입니다. 어느 경우든 라운드 수를 소비합니다.

**검토 범위:** 리뷰어가 결과 안에서 diff 절단, 일부 파일만 검토, 파싱 실패 후 재구성(salvage) 같은 **부분 검토**를 자기 보고하면 그 결과를 `부분 결과`로 기록합니다. 부분 결과도 정족수를 채우고 라운드는 통과로 진행할 수 있습니다. 대신 §5의 무효 판정과 같은 흐름으로, merge 직전 확인 단계에서 **어느 리뷰어의 어떤 결과가 부분이었고 무엇이 검토되지 않았는지** 사용자에게 전부 제시합니다. 부분 결과인 `approve`는 검토된 범위에 대한 approve일 뿐입니다. 같은 리뷰어의 부분 결과가 라운드마다 반복되면 PR 규모 문제이므로 §8에 따라 분할을 제안합니다.

**정족수:** 통과 판정은 **상시 리뷰어 전원의 결과가 같은 head에 대해 도착했을 때만** 합니다. 도착한 결과만으로 통과를 선언하지 마세요. 늦게 도착하는 리뷰어가 차단 finding을 가지고 있을 수 있습니다.

**타임아웃:** `reviewer_timeout`을 넘겨도 결과가 오지 않으면 그 리뷰어를 `결과 없음`으로 기록하고 라운드를 진행합니다. 무응답의 의미는 리뷰어마다 다릅니다.

- 문제가 없을 때 결과를 남기지 않는 리뷰어의 무응답은 정상이며 `finding 없음`으로 취급할 수 있습니다.
- 문제가 없을 때도 항상 결과를 남기는 리뷰어의 무응답은 장애 신호입니다. `finding 없음`으로 취급하지 마세요.

`결과 없음`인 상시 리뷰어가 있으면 자동으로 통과를 선언하지 않습니다. 나머지 리뷰어가 모두 통과 기준을 만족하더라도 §6의 merge 확인 단계에서 **어느 리뷰어의 결과가 빠졌는지 명시하고** 사용자 판단을 받습니다. `on_pass = merge 안 함`이면 통과·미병합으로 처리하지 않고, 결과 부족으로 판정을 보류한 **지시 대기** 상태를 보고합니다.

**중요도 정규화:** [REVIEW.md](./REVIEW.md)의 P 척도를 쓰지 않는 리뷰어(High/Medium/Low 같은 자체 라벨, 또는 라벨 없음)의 finding은 실행 주체가 REVIEW.md 「Severity」 정의로 중요도를 재판정합니다. 리뷰어의 원 라벨은 판정 기록의 리뷰어 열에 함께 남깁니다. 재판정은 정의 대조이며 finding을 깎는 수단이 아닙니다 — 발생 조건부터 영향까지 end-to-end로 추적되면 그 정의에 맞는 값을 주고, 추적이 되지 않으면 P2 이하로 두되 `blocking`은 별도로 판단합니다. 리뷰어가 P 척도를 쓰더라도 정의와 명백히 어긋나면 같은 방식으로 재판정하고 그 근거를 남깁니다.

**중복 통합:** 같은 원인의 finding은 하나로 합칩니다.

- 중요도는 **가장 높은 값**을 채택합니다.
- `blocking`은 **하나라도 `true`이면 `true`**입니다.
- 어느 리뷰어가 각각 무엇으로 보고했는지 남깁니다.

**verdict는 합치지 않습니다.** 리뷰어가 낸 `approve`·`request_changes` 같은 판정은 참고 신호일 뿐 임계값 계산에 쓰지 않습니다. 리뷰어끼리 verdict가 엇갈리는 것은 판정 충돌이 아니라 한쪽이 다른 쪽이 보지 못한 finding을 가지고 있다는 뜻입니다. 그 finding을 §5에 따라 판정하면 충돌은 사라집니다.

## 5. Finding 판정

각 finding을 **유효** 또는 **무효** 중 하나로 판정합니다. 무효로 판정한 finding은 임계값 계산에 넣지 않습니다.

무효로 판정할 수 있는 경우:

- [REVIEW.md](./REVIEW.md) §8 Do Not Report에 해당
- 지적된 동작이 실제 코드에서 성립하지 않음
- 이미 다른 코드 경로에서 처리되고 있음

`blocking=false`는 무효 사유가 아닙니다. 기존 결함, 이월 작업, 의도적으로 단계화된 설계에서 확인된 결함도 유효성을 판정하고 `blocking`은 별도로 표시합니다. [REVIEW.md](./REVIEW.md) §3 Review Scope가 보고 대상으로 허용한 검증된 P0·P1을 관련 없는 기존 문제라는 이유로 무효 처리하지 마세요. **기본 임계값에서는 `blocking=false`인 P0·P1도 집계하고, 비차단 P2와 모든 P3만 통과를 막지 않습니다.** 승인된 deferral도 기본 임계값의 P0·P1 예외가 되지 않습니다. 사용자가 다른 임계값을 지정했다면 §2의 확정값으로 판단합니다.

무효 판정에는 반드시 다음을 남깁니다.

- **반증 근거:** 파일과 줄 번호, 또는 실행한 명령과 그 출력
- 위 사유 중 어디에 해당하는지
- 반증이 성립하는 조건과 그 조건이 깨지는 경우

이 문서는 [REVIEW.md](./REVIEW.md)를 절 번호와 헤딩명을 함께 써서 참조합니다. 기존 저장소의 REVIEW.md와 병합해 번호가 달라졌거나 없어졌다면 헤딩명을 기준으로 참조를 고치세요. 번호만 남기면 라운드 진행자가 근거 절을 찾지 못합니다.

무효 판정은 사용자 확인 없이 수행합니다. 대신 근거를 원장에 남기고, merge 직전 확인 단계에서 무효 판정 **전체**를 사용자에게 제시합니다. **근거를 쓸 수 없으면 유효로 취급합니다.**

같은 원인의 지적이 반복되면 기존 판정과 근거를 대조합니다. 관련 코드·계약·전제에 변화가 없고 새 증거도 없으면 기존 판정을 재사용합니다. 새 증거가 있거나 수정으로 전제가 바뀌면 다시 검증하며, 반복 지적이라는 이유만으로 버리지 않습니다.

## 6. 통과 판정과 종료 분기

```text
[2. 리뷰 확인] 정족수 충족 → 통합 → 판정 → 확정한 임계값 평가
        │
        ├─ 통과 → head 동결·세션 인계 목록 확정
        │           ├─ merge 안 함 → 통과·미병합 보고 → 종료
        │           └─ merge → 사용자 확인 → 상태 확인 → 동일 head merge → 종료
        │                (문서 반영은 다음 작업에서 수행합니다)
        │
        └─ 미통과 → [3. 수정] → [4. commit]
                        │
                        ├─ 라운드 남음 ─→ [1. 리뷰 대기]
                        │
                        └─ 라운드 소진 ─→ merge하지 않고 연장 제안 후 지시 대기
```

**통과한 경우:**

1. **통과한 head를 동결합니다.** 통과를 판정한 리뷰를 이 head의 마지막 리뷰로 삼습니다. 통과 후에는 코드 수정이나 기록용 commit·push, 추가 재리뷰 요청을 하지 않습니다.
2. **남은 유효 finding을 세션 인계 목록에 기록합니다.** 이관 가능한 항목은 확정한 임계값에서 남겨도 되는 항목입니다. 기본값에서는 비차단 P2와 모든 P3이며, 사용자 지정값에서는 달라질 수 있습니다. 이 단계에서 [02-TODO.md](./02-TODO.md)·[REVIEW.md](./REVIEW.md) 등 tracked 파일을 수정하거나 PR 판정 댓글을 게시하지 않습니다. 인계 형식은 §7을 따릅니다.

`on_pass = merge 안 함`이면 통과한 대상 revision, 검증 결과, 무효 판정 근거, 누락·부분 리뷰와 인계 목록을 보고하고 **통과·미병합**으로 종료합니다. PR이 없으면 비교 기준 revision과 검토한 로컬 변경 범위도 명시합니다. 나중에 merge를 요청받으면 그때 대상 상태와 병합 조건을 다시 확인하며, 이번 종료를 merge 승인으로 해석하지 않습니다.

`on_pass = 사용자 확인 후 merge`이면 다음을 따릅니다.

1. merge 전에 사용자에게 확인을 요청합니다. 확인 요청에는 대상 head·base, **실제 적용한 임계값**, 진행한 라운드 수, 검증 결과, 결과가 도착한 리뷰어와 `결과 없음`으로 처리한 리뷰어, **`부분 결과`로 처리한 리뷰어와 검토되지 않은 범위**, **무효로 판정한 finding 전체와 그 근거**, 인계 목록을 포함합니다.
2. 확인을 받은 뒤 **병합 직전 상태만 확인합니다.** head·base가 승인 대상과 같은지, 필수 검사가 충족되었는지, 새 리뷰 결과가 도착했는지 확인합니다. head·base가 바뀌면 §3·§4에 따라 리뷰로 돌아갑니다. 새 결과는 §5와 확정한 임계값으로 판정하며, 통과를 막으면 수정 단계로 돌아갑니다. 통과를 막지 않는 새 항목은 세션 인계 목록에 추가하고 사용자에게 알립니다. 필수 검사가 실패하거나 대기 중이면 병합하지 않습니다.
3. **승인받은 head와 일치하는 커밋만 merge**합니다. head 불일치로 병합이 거부되면 새 head를 무조건 병합하지 말고 앞 단계로 돌아갑니다. 실제 merge 결과와 merge commit SHA를 세션 종료 보고에 남깁니다. branch는 삭제하지 않습니다.

처리한 finding의 인라인 스레드는 해소 표시를 합니다. 미해결 스레드가 병합 조건인 저장소도 있고, 남겨 두면 다음 라운드에서 이미 처리한 것을 다시 집계하게 됩니다. **처리하지 않은 finding의 스레드를 정리 목적으로 닫지는 마세요.**

통과 후 인계·완료 기록을 저장소 파일에 쓰는 작업은 §9에 따라 **다음 작업에서** 수행합니다. 기록만을 위한 push로 현재 PR의 리뷰를 다시 시작하지 않습니다. 통과를 막는 새 결함이나 필수 검증 실패를 이관 기록으로 대신 처리하지 않습니다.

**미통과 & 라운드 소진:** 수정과 commit까지만 수행하고 merge하지 않습니다. 다음을 함께 보고하고 지시를 기다립니다.

- 확정한 임계값에서 통과를 막는 미해소 finding과 각각의 상태 (기본값에서는 `blocking=false`인 P0·P1 포함)
- 수렴하지 않는 원인 — 같은 원인이 반복되는지, 수정할 때마다 새 결함이 나오는지
- 라운드 연장이 타당한지에 대한 판단과 제안 라운드 수

기본 임계값에서 비차단 P0·P1이 남아 있으면 미통과입니다. 보고하거나 후속 작업으로 등록하는 것만으로 통과 처리하지 않습니다. 사용자가 임계값을 변경한 경우에는 §2에 따라 새 기준으로 재평가합니다.

## 7. 원장

라운드는 리뷰 대기 상태에서 세션을 넘길 수 있으므로 진행 상태를 남깁니다.

**리뷰 도구가 이미 PR에 결과를 남기고 있다면 그 코멘트가 원장입니다.** 같은 내용을 다시 만들지 마세요.

단, 코멘트 하나를 head마다 덮어쓰는(sticky) 리뷰어는 이전 라운드의 결과가 사라집니다. 그 리뷰어의 finding은 판정 기록에 ID·요지·중요도를 남겨 두어야 다음 라운드에서 해소 여부를 대조할 수 있습니다. §2.1의 `게시 위치`에 덮어쓰기 여부를 적어 두는 이유입니다.

**판정 기록의 위치.** PR 유무와 실행 모드에 관계없이 판정 기록은 실행 주체의 세션 안에서 유지하고 라운드마다 사용자에게 보고합니다(§10). tracked 파일에 쓰면 리뷰 대상이 바뀌므로 [02-TODO.md](./02-TODO.md)에 임시 원장을 만들지 않습니다. PR 판정 댓글도 게시하지 않습니다. 세션을 넘겨야 하면 마지막 §10 보고를 다음 세션의 입력으로 전달하고, PR이 있다면 그곳의 리뷰어 결과와 함께 원장을 재구성합니다.

- **읽기:** 각 리뷰어의 결과를 head SHA로 정렬해 읽습니다. 대부분의 리뷰 도구는 코멘트에 head SHA나 라운드 번호를 남깁니다. 그것으로 라운드 경계와 §4의 정족수를 판단합니다.
- **쓰기:** 라운드마다 **판정 결과만** 별도로 남깁니다. 리뷰어가 이미 쓴 finding 본문을 복제하지 않습니다.
- 기록 위치는 위 「판정 기록의 위치」를 따릅니다.
- **수명:** 종료 보고를 다음 작업의 인계 자료로 유지합니다. 저장소 문서 반영은 §9에 따라 다음 작업에서 수행합니다. `통과·미병합`이면 병합된 것으로 기록하지 않습니다.

판정 기록에는 대상, 확정한 파라미터와 사용자가 요청한 변경 이력, 현재 라운드와 최대 라운드, 라운드별 head·base와 결과가 도착한 리뷰어(`부분 결과`·`결과 없음` 표시 포함), `rereview = request`였다면 라운드별로 요청을 보낸 리뷰어와 접수 확인 결과, 검증 결과를 남기고 finding은 다음 형식으로 정리합니다.

| ID | 라운드 | head | 리뷰어 | 중요도 | confidence | blocking | 판정 | 근거 | 처리 | commit |
|---|---|---|---|---|---|---|---|---|---|---|
| F-001 | 1 | `abc123` | A, B | P1 | 0.9 | true | 유효 | 근거 | 수정 | SHA |

`리뷰어` 열에는 같은 finding을 보고한 리뷰어를 모두 적고, 중요도가 서로 달랐다면 각각의 값도 남깁니다.

**세션 인계 목록:** 원 PR·head·base(로컬 리뷰면 비교 기준과 변경 범위), 실제 적용한 임계값, 원 finding 링크/ID, 중요도·`blocking`·판정 근거, 남은 작업과 완료 조건을 포함합니다. 각 항목은 `문서 반영 대기`로 표시하고, 기존 추적 항목이 있으면 그 위치를 연결합니다. 종료 시 merge 여부와 실제 merge SHA도 남깁니다. 인계 목록 작성이나 merge만으로 다음 작업이 시작되거나 저장소 문서 반영이 완료된 것은 아닙니다.

## 8. 조기 중단

라운드 예산이 남아 있어도 다음 경우에는 중단하고 지시를 기다립니다.

- 같은 모듈에서 라운드마다 확정한 임계값의 통과를 막는 새 P0·P1이 발생하는 경우 — 개별 결함이 아니라 설계 문제 신호입니다
- 수정이 [00-PROJECT.md](./00-PROJECT.md)의 확정된 결정과 충돌하는 경우
- 수정에 요청 범위를 넘는 광범위한 리팩터링이 필요한 경우
- 검증 명령을 실행할 수 없어 수정의 안전성을 확인할 수 없는 경우
- 상시 리뷰어가 라운드마다 타임아웃되는 경우 — 개별 결함이 아니라 리뷰 파이프라인 장애 신호입니다
- 같은 리뷰어가 라운드마다 `부분 결과`를 내는 경우 — PR이 리뷰어의 처리 한도를 넘었다는 신호입니다. 분할을 제안합니다

## 9. 다음 작업의 문서 반영

- **현재 라운드는 세션 종료 보고로 끝냅니다.** 문서 반영을 위해 별도 branch·PR·이슈를 자동 생성하거나 merge 후 추가 commit·push하지 않습니다.
- 사용자가 다음 관련 구현·문서 수정 작업을 시작하면 세션 인계 목록을 먼저 확인하고, 그 작업의 문서 변경에 함께 반영합니다. 다른 세션이라면 이전 종료 보고를 입력으로 전달받습니다. 인계 내용을 확보하지 못했다면 GitHub 원문 등으로 확인 가능한 항목만 복원하고 빠진 판정 근거를 명시합니다. 분석·일반 리뷰·질문 답변만 요청받았다면 문서를 수정하지 않습니다.
- 남은 항목은 [02-TODO.md](./02-TODO.md) `Backlog`에 변경 단위로 연결합니다. 원 PR 또는 로컬 기준 revision, finding ID, 판정 근거, 남은 작업·완료 조건의 상세는 기존 변경별 PLAN이 있으면 그곳에, 없으면 TODO 항목에 한 번만 기록합니다. 기존 항목을 중복 생성하지 않습니다. [REVIEW.md](./REVIEW.md) §9 Accepted Deferrals에는 해당 정책의 승인 요건을 충족한 경우에만 등록합니다. 한 라운드의 임계값 변경을 영구 deferral로 바꾸지 않습니다.
- 이전 작업의 실제 통합과 완료 조건을 확인한 뒤에만 전역 TODO의 완료 표시를 반영합니다. 변경별 PLAN에는 확인한 브랜치의 구현·검증 상태를 기록하며 이를 병합·릴리스로 해석하지 않습니다. PR 없는 작업은 합의된 로컬 대상과 검토한 revision 또는 작업 트리 범위로 확인합니다. `통과·미병합`을 통합 완료로, 이관 항목을 해결 완료로 표시하지 않습니다.
- [00-PROJECT.md](./00-PROJECT.md)는 실제 결정·구현·지원 범위가 바뀐 경우에만 갱신합니다. 문서 반영은 다음 PR 또는 로컬 검토 단위의 변경 범위로 검토받으며, 이전 검토의 통과 상태를 다시 열지 않습니다. 후속 작업이 아직 없으면 인계 항목은 `문서 반영 대기`로 유지합니다.

## 10. 종료 보고

라운드가 끝나면 한국어로 다음을 보고합니다.

- 진행한 라운드 수와 최종 상태 (merge / 통과·미병합 / 지시 대기 / 중단)
- 실제 적용한 임계값과 사용자 요청에 따른 변경 이력
- 라운드별 head, 결과가 도착한 리뷰어, `부분 결과`와 `결과 없음`으로 처리한 리뷰어, finding 수와 판정 결과
- 리뷰어별로 다르게 보고된 finding과 통합 결과
- 무효로 판정한 finding과 그 근거 요약
- 수행한 수정과 commit
- 실행한 검증과 그 결과, 실행하지 못한 검증과 이유
- 다음 작업에 전달할 세션 인계 목록, 문서 반영 대기 상태와 실제 merge 결과
