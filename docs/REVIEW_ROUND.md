# Review Round Protocol

이 문서는 사용자가 **리뷰 라운드를 명시적으로 시작한 경우에만** 적용합니다. 일반적인 PR·diff 리뷰 요청에는 [REVIEW.md](./REVIEW.md)만 적용하고 이 절차를 적용하지 않습니다.

[REVIEW.md](./REVIEW.md)가 **무엇을 결함으로 판단하는가**를 정의한다면, 이 문서는 **그 결과를 받아 누가 언제 수정·commit·merge하는가**를 정의합니다.

## Metadata

- **Status:** Active
- **Owner:** 프로젝트에 맞게 작성
- **Last reviewed:** YYYY-MM-DD
- **Review cadence:** 라운드 정책 또는 권한 위임 범위 변경 시

## 1. 권한 위임

[AGENTS.md](../AGENTS.md)는 명시적인 요청 없는 commit, push, branch 삭제 및 배포를 금지합니다. 라운드 시작은 그 금지에 대한 **범위가 한정된 예외**입니다.

**위임되는 것** — 시작 시 확정한 파라미터 범위 안에서만:

- 유효한 finding에 대한 코드 수정
- 라운드별 commit
- 대상 branch로의 non-force push. 리뷰어가 push로 트리거되는 구성에서는 push 없이 다음 라운드가 시작되지 않습니다
- `rereview = request`일 때, §2.1 표에 등록된 방법으로의 **재리뷰 요청** — 트리거 댓글 게시 또는 리뷰어 재요청 API 호출. 등록된 문구·호출을 그대로 사용하며 임의로 변형하지 않습니다
- §6에 따라 **처리한 finding의 인라인 스레드를 해소 표시**하는 것. 처리하지 않은 finding의 스레드는 닫지 않습니다
- 통과 시 **사용자 확인을 거친** merge

**위임되지 않는 것:**

- branch 삭제 (로컬·원격 모두)
- force push 및 history 재작성
- 대상 branch 밖의 파일 또는 branch 변경
- 재리뷰 요청 이외의 PR 댓글, 그리고 리뷰어에게 코드 수정을 지시하는 멘션. 일부 리뷰어는 트리거 문구 뒤에 다른 말이 붙으면 리뷰 대신 코드를 수정하는 태스크를 시작하고 branch에 push합니다. 그 push는 위임 범위 밖입니다
- 배포, 릴리스 게시, tag 생성, 마이그레이션 실행, 의존성 설치
- 라운드 수와 임계값의 임의 변경
- 사용자 확인 없는 merge

이 문서를 읽지 않은 실행에서는 [AGENTS.md](../AGENTS.md)의 기본 금지 규칙이 그대로 적용됩니다.

## 2. 파라미터

| 파라미터 | 기본값 | 설명 |
|---|---|---|
| `rounds` | `5` | 최대 라운드 수 |
| `threshold` | `blocking P0·P1·P2 = 0` | 통과 임계값. [REVIEW.md](./REVIEW.md) §4.3 Blocking의 `blocking` 값을 사용합니다 |
| `target` | 현재 branch 또는 PR | 라운드 대상 |
| `reviewers` | §2.1의 상시 리뷰어 전체 | 결과를 기다릴 리뷰어. 등록 항목은 §2.1. `self`로 지정하면 외부 리뷰어 없이 실행 주체가 [REVIEW.md](./REVIEW.md)로 직접 리뷰합니다. 이 경우 §4의 정족수·타임아웃·head 정렬은 적용하지 않고, 원장은 [TODO.md](./TODO.md) 임시 블록을 사용합니다 |
| `reviewer_timeout` | `45분` | 한 리뷰어의 결과를 기다리는 최대 시간 |
| `rereview` | `auto` | 라운드 안의 push 뒤 재리뷰를 어떻게 받는지. `auto`는 리뷰어 자체 트리거에만 의존합니다. `request`는 §2.1 표의 `재리뷰 요청 방법`이 등록된 리뷰어에게 실행 주체가 직접 요청합니다(§3). 사용자가 지정할 때만 `request`로 합니다 |
| `on_pass` | 사용자 확인 후 merge | `merge 안 함`으로 변경 가능 |
| `close_branch` | 하지 않음 | 위임 대상이 아닙니다 |

시작 전에 확정한 파라미터를 사용자에게 되읽어 주고 시작합니다. 되읽기 없이 라운드를 시작하지 않습니다. `rereview = auto`인데 §2.1의 상시 리뷰어 중 `재리뷰 요청 방법`이 `push 자동`인 리뷰어가 하나도 없으면, 2라운드부터 상시 리뷰어의 결과가 오지 않아 정족수를 채울 수 없다는 점을 되읽기에 포함하고 `request`로 바꿀지 묻습니다. 사용자가 `auto`를 유지하면 그대로 진행합니다.

PR 규모와 리뷰어 수에 따라 실제 필요한 라운드 수는 크게 달라집니다. `rounds`는 시작점일 뿐이며, 소진 시 §6에 따라 연장을 제안합니다.

기본 임계값은 [REVIEW.md](./REVIEW.md) §10 Review Conclusion의 verdict 규칙보다 엄격합니다. verdict는 blocking P0·P1에서만 `request_changes`가 되지만, 라운드는 Blocking P2도 통과를 막습니다.

### 2.1 리뷰어 등록

이 표는 템플릿 적용 시 Maintainer가 작성합니다. 이 저장소에서 실제로 도는 리뷰어를 **전부** 조사해 기록합니다. 리뷰어를 누락하면 §4의 정족수 판정이 틀립니다. 라운드 실행 중에는 이 문서를 수정하지 않으며, 표가 비어 있으면 라운드를 시작하지 않고 등록을 요청합니다.

리뷰어는 **도착 주기**로 나뉩니다. 이 구분은 **기다릴지 여부만** 가르며 finding의 가치를 가르지 않습니다.

- **상시 리뷰어:** 변경마다 결과를 남깁니다. §4의 정족수 대상입니다.
- **간헐 리뷰어:** 일부 변경에만, 또는 PR당 한 번만 결과를 남깁니다. 정족수 대상이 아니며 도착한 라운드에서만 pool에 추가합니다. PR당 1회만 도는 리뷰어를 정족수에 넣으면 두 번째 라운드부터 영원히 채울 수 없습니다.

| 리뷰어 | 게시 위치 | head 식별 방법 | 도착 주기 | 문제가 없을 때 | 재리뷰 요청 방법 |
|---|---|---|---|---|---|

각 열에 기록할 내용입니다.

- **게시 위치:** PR 코멘트인지, PR review 본문인지, 인라인 스레드인지. **여러 곳에 나눠 쓰는 리뷰어는 그 전부를 적습니다.** PR 코멘트라면 head마다 새 코멘트를 남기는지, 코멘트 하나를 덮어쓰는지(sticky)도 적습니다. 덮어쓰는 리뷰어는 §7의 원장 규칙이 달라집니다
- **head 식별 방법:** 그 결과가 어느 커밋을 본 것인지 알아내는 방법. 마커 주석, 본문의 SHA, 라운드 번호 등
- **도착 주기:** 상시 또는 간헐. 간헐이면 어떤 조건에서 도는지
- **문제가 없을 때:** 결과를 남기는지 여부. §4의 타임아웃 처리가 이 값에 따라 달라집니다
- **재리뷰 요청 방법:** 새 push에 대해 리뷰를 다시 받는 방법. 다음 중 하나를 적습니다.
  - `push 자동` — push마다 스스로 다시 돕니다. 트리거 조건(ruleset, workflow 이벤트 등)을 함께 적습니다
  - 요청 방법 — 정확한 트리거 댓글 본문 또는 API 호출과, **요청이 접수되었는지 확인하는 방법**(반응 이모지, REST `requested_reviewers` 또는 GraphQL `reviewRequests`에 리뷰어가 포함되는지 등. 리뷰어가 실행을 시작하면 요청 목록에서 빠지는 경우가 있으므로 확인은 호출 직후에 합니다). `rereview = request`일 때 실행 주체가 이 열을 그대로 실행합니다
  - `불가` — 재리뷰 수단이 없습니다. 이 리뷰어는 도착 주기가 간헐이어야 합니다

"PR당 1회"인 공개 리뷰어는 이 열이 비어 있으면 `rereview = request`로도 재리뷰를 받을 수 없습니다. 자동 리뷰가 켜져 있어도 대개 PR을 열 때 한 번만 돌고 push마다 돌지 않으므로, 도구 문서에서 재요청 방법을 확인해 적어 두세요.

## 3. 한 라운드의 4단계

```text
[1. 리뷰 대기] → [2. 리뷰 확인] → [3. 수정] → [4. commit]
```

**1. 리뷰 대기** — 리뷰를 요청하고 결과가 도착할 때까지 대상 코드를 동결합니다. 리뷰어마다 소요 시간이 다르므로 §4의 정족수 조건을 충족하거나 `reviewer_timeout`에 도달할 때까지 기다립니다. 요청 방식은 다음과 같습니다.

- **1라운드:** 대상 PR에 현재 head를 본 결과가 이미 있으면 그것을 사용하며 다시 요청하지 않습니다. PR을 열 때 자동으로 도는 리뷰어는 이 시점에 이미 결과를 남겼습니다.
- **push가 있었던 라운드:** §2.1 표의 `재리뷰 요청 방법`이 `push 자동`인 리뷰어는 push 자체가 요청입니다. 그 외 리뷰어는 `rereview` 값에 따릅니다.
  - `auto` — 요청하지 않고 기다립니다. 결과가 오지 않으면 §4의 타임아웃 규칙을 적용합니다.
  - `request` — push 직후 표에 적힌 방법을 **그대로** 실행합니다. 트리거 댓글은 등록된 본문만 담고 다른 문장을 덧붙이지 않습니다. 실행 직후 표의 확인 방법으로 접수 여부를 확인하고, 접수되지 않았으면 `reviewer_timeout`을 기다리지 않고 즉시 사용자에게 보고합니다. 일부 리뷰어의 재요청 API는 성공 응답을 돌려주면서 실제로는 아무 일도 하지 않으므로 응답 코드만으로 접수를 판단하지 마세요. **접수가 확인된 리뷰어는 그 라운드에 한해 §4의 정족수에 포함합니다** — 결과가 도착하거나 `reviewer_timeout`에 이를 때까지 기다립니다. 상시 리뷰어가 먼저 도착했다는 이유로 요청한 리뷰를 기다리지 않고 통과를 판정하면 이 모드를 쓰는 이유가 없어집니다.
- **push가 없었던 라운드:** 재리뷰를 요청하지 않습니다. 같은 head에 대한 두 번째 리뷰는 라운드가 아닙니다. 예외는 §4의 **base 변경**입니다. base가 바뀐 라운드는 head가 같아도 diff가 다르므로 push가 있었던 라운드와 같이 처리합니다 — `rereview = request`면 요청하고, `auto`면 기다립니다. `push 자동` 리뷰어의 트리거가 base 변경을 포함하지 않으면(retarget은 `synchronize`가 아니라 `edited`입니다) 결과가 오지 않으므로 §4의 타임아웃 규칙에 따라 `결과 없음`으로 기록하고 §6 확인 단계에서 명시합니다.

**2. 리뷰 확인** — 도착한 결과를 §4에 따라 통합하고, finding별로 유효·무효를 판정하고(§5), 임계값을 평가합니다. **통과 판정은 이 시점에 합니다.**

**3. 수정** — 유효하고 blocking인 finding을 수정합니다. 비차단 finding을 함께 수정할 수 있으며, 그 수정은 다음 라운드에서 리뷰됩니다.

**4. commit** — 위험에 비례해 [AGENTS.md](../AGENTS.md)의 Build, Test, Lint, Typecheck를 실행하고 결과를 기록합니다. 생성 파일이 있는 저장소는 재생성과 생성물 검사까지가 검증입니다. 과금이 발생하거나 외부 서비스를 호출하는 검증은 라운드 안에서 실행하지 않습니다. 라운드는 같은 검증을 여러 번 돌리므로 비용과 부작용이 누적됩니다. 검증이 실패하면 commit하지 않고 보고합니다. 커밋 메시지에 라운드 번호와 처리한 finding ID를 남깁니다.

## 4. 여러 리뷰어의 결과 통합

`reviewers = self`이면 이 절을 건너뛰고 §5로 진행합니다.

리뷰어를 여럿 두는 목적은 한 리뷰어가 놓친 것을 다른 리뷰어가 잡는 것입니다. 따라서 **finding은 전원의 것을 모두 모으고, 어느 것도 리뷰어를 이유로 버리지 않습니다.** finding의 무게에 리뷰어별 등급을 두지 않습니다. §2.1의 상시·간헐 구분은 **기다릴지 여부만** 가르며 finding의 가치를 가르지 않습니다.

**수집:** 도착한 모든 리뷰어의 finding을 하나의 pool로 모읍니다. **한 리뷰어의 결과는 여러 곳에 나뉘어 있습니다.** 최소한 다음을 모두 읽으세요.

- PR 코멘트 (봇의 sticky 코멘트 포함)
- PR review의 top-level 본문
- **줄에 붙은 인라인 리뷰 스레드** — 미해결·해결 모두
- 스레드의 후속 답글. 첫 코멘트만 읽으면 철회되거나 보강된 내용을 놓칩니다
- review 본문의 **접힌 `<details>` 블록**. 일부 리뷰어는 저신뢰 finding을 "Suppressed comments" 같은 접힌 블록에 넣습니다. 접혀 있다는 이유로 finding이 아닌 것은 아니며, §5에 따라 판정합니다

**top-level 요약이 그 리뷰어의 finding을 전부 담는다고 가정하지 마세요.** 요약이 "결함 없음"이나 `approve`인데 인라인에 차단 finding이 달려 있는 경우가 실제로 있습니다. 요약과 인라인이 다르면 인라인이 더 구체적인 근거를 가진 쪽입니다.

미해결 스레드 목록은 그 자체로 신호입니다. 라운드를 시작할 때와 통과를 판정할 때 각각 확인하세요.

**head 정렬:** 각 결과가 어느 head를 본 것인지 확인합니다. 현재 head와 다른 head를 본 결과는 이번 라운드의 판정 근거로 쓰지 않습니다. 단 head 표시가 없고 PR당 한 번만 도착하는 리뷰어는 예외이며, 그 finding이 현재 head에서 해소되었는지 코드로 직접 확인하고 근거를 남깁니다. 오래되었다는 이유만으로 버리지 마세요.

**base 변경:** PR의 base가 바뀐 경우 — 다른 branch로 retarget, base branch를 merge 또는 rebase, stacked PR의 아래 PR이 병합됨 — 리뷰어가 본 diff와 현재 diff가 다릅니다. head SHA가 같아 보여도 이전 결과는 판정 근거로 쓰지 않고 새 라운드로 셉니다. 실행 주체가 할 수 있는 base 변경은 base branch를 대상 branch에 **merge**하는 것뿐이며 §1의 non-force push 범위 안입니다. rebase는 force push를 요구하므로 위임되지 않고, retarget과 아래 PR의 병합은 라운드 밖에서 일어나는 변경입니다. 어느 경우든 라운드 수를 소비합니다.

**검토 범위:** 리뷰어가 결과 안에서 diff 절단, 일부 파일만 검토, 파싱 실패 후 재구성(salvage) 같은 **부분 검토**를 자기 보고하면 그 결과를 `부분 결과`로 기록합니다. 부분 결과도 정족수를 채우고 라운드는 통과로 진행할 수 있습니다. 대신 §5의 무효 판정과 같은 흐름으로, merge 직전 확인 단계에서 **어느 리뷰어의 어떤 결과가 부분이었고 무엇이 검토되지 않았는지** 사용자에게 전부 제시합니다. 부분 결과인 `approve`는 검토된 범위에 대한 approve일 뿐입니다. 같은 리뷰어의 부분 결과가 라운드마다 반복되면 PR 규모 문제이므로 §8에 따라 분할을 제안합니다.

**정족수:** 통과 판정은 **상시 리뷰어 전원의 결과가 같은 head에 대해 도착했을 때만** 합니다. 도착한 결과만으로 통과를 선언하지 마세요. 늦게 도착하는 리뷰어가 차단 finding을 가지고 있을 수 있습니다.

**타임아웃:** `reviewer_timeout`을 넘겨도 결과가 오지 않으면 그 리뷰어를 `결과 없음`으로 기록하고 라운드를 진행합니다. 무응답의 의미는 리뷰어마다 다릅니다.

- 문제가 없을 때 결과를 남기지 않는 리뷰어의 무응답은 정상이며 `finding 없음`으로 취급할 수 있습니다.
- 문제가 없을 때도 항상 결과를 남기는 리뷰어의 무응답은 장애 신호입니다. `finding 없음`으로 취급하지 마세요.

`결과 없음`인 상시 리뷰어가 있으면 자동으로 통과를 선언하지 않습니다. 나머지 리뷰어가 모두 통과 기준을 만족하더라도 §6의 merge 확인 단계에서 **어느 리뷰어의 결과가 빠졌는지 명시하고** 사용자 판단을 받습니다.

**중복 통합:** 같은 원인의 finding은 하나로 합칩니다.

- 중요도는 **가장 높은 값**을 채택합니다.
- `blocking`은 **하나라도 `true`이면 `true`**입니다.
- 어느 리뷰어가 각각 무엇으로 보고했는지 남깁니다.

**verdict는 합치지 않습니다.** 리뷰어가 낸 `approve`·`request_changes` 같은 판정은 참고 신호일 뿐 임계값 계산에 쓰지 않습니다. 리뷰어끼리 verdict가 엇갈리는 것은 판정 충돌이 아니라 한쪽이 다른 쪽이 보지 못한 finding을 가지고 있다는 뜻입니다. 그 finding을 §5에 따라 판정하면 충돌은 사라집니다.

## 5. Finding 판정

각 finding을 **유효** 또는 **무효** 중 하나로 판정합니다. 무효로 판정한 finding은 임계값 계산에 넣지 않습니다.

무효로 판정할 수 있는 경우:

- [REVIEW.md](./REVIEW.md) §8 Do Not Report에 해당
- 지적된 동작이 실제 코드에서 성립하지 않음
- 이미 다른 코드 경로에서 처리되고 있음

`blocking=false`는 무효 사유가 아닙니다. 기존 결함, 이월 작업, 의도적으로 단계화된 설계는 **유효한 finding이되 임계값 계산에서만 빠집니다.** 무효로 처리하면 §6의 이관 대상에서도 사라져 기록이 없어집니다. 유효성은 사실 여부로만 판단하고, blocking 여부는 그와 별개로 표시하세요.

무효 판정에는 반드시 다음을 남깁니다.

- **반증 근거:** 파일과 줄 번호, 또는 실행한 명령과 그 출력
- 위 사유 중 어디에 해당하는지
- 반증이 성립하는 조건과 그 조건이 깨지는 경우

이 문서는 [REVIEW.md](./REVIEW.md)를 절 번호와 헤딩명을 함께 써서 참조합니다. 기존 저장소의 REVIEW.md와 병합해 번호가 달라졌거나 없어졌다면 헤딩명을 기준으로 참조를 고치세요. 번호만 남기면 라운드 진행자가 근거 절을 찾지 못합니다.

무효 판정은 사용자 확인 없이 수행합니다. 대신 근거를 원장에 남기고, merge 직전 확인 단계에서 무효 판정 **전체**를 사용자에게 제시합니다. **근거를 쓸 수 없으면 유효로 취급합니다.**

## 6. 통과 판정과 종료 분기

```text
[2. 리뷰 확인] 정족수 충족 → 통합 → 판정 → 임계값 평가
        │
        ├─ 통과 ─→ 비차단 finding 이관 → 사용자 확인 → merge → 종료
        │           (이 라운드에서는 수정도 commit도 하지 않습니다)
        │
        └─ 미통과 → [3. 수정] → [4. commit]
                        │
                        ├─ 라운드 남음 ─→ [1. 리뷰 대기]
                        │
                        └─ 라운드 소진 ─→ merge하지 않고 연장 제안 후 지시 대기
```

**통과한 경우:**

1. 남은 비차단 finding을 **고치지 않고 이관**합니다. [TODO.md](./TODO.md)의 `Backlog` 또는 [REVIEW.md](./REVIEW.md) §9 Accepted Deferrals에 등록하고, 다음 PR에서 다루도록 남깁니다.
2. merge 전에 사용자에게 확인을 요청합니다. 확인 요청에는 대상, 진행한 라운드 수, 결과가 도착한 리뷰어와 `결과 없음`으로 처리한 리뷰어, **`부분 결과`로 처리한 리뷰어와 검토되지 않은 범위**, **무효로 판정한 finding 전체와 그 근거**, 이관 항목을 포함합니다.
3. 확인을 받은 뒤 merge합니다. branch는 삭제하지 않습니다.

처리한 finding의 인라인 스레드는 해소 표시를 합니다. 미해결 스레드가 병합 조건인 저장소도 있고, 남겨 두면 다음 라운드에서 이미 처리한 것을 다시 집계하게 됩니다. **처리하지 않은 finding의 스레드를 정리 목적으로 닫지는 마세요.**

통과한 라운드에서 수정과 commit을 하지 않는 이유는, 리뷰를 거치지 않은 커밋이 병합되는 경로를 만들지 않기 위해서입니다. 통과 후에 발견한 수정 필요 사항은 다음 PR로 넘깁니다.

**미통과 & 라운드 소진:** 수정과 commit까지만 수행하고 merge하지 않습니다. 다음을 함께 보고하고 지시를 기다립니다.

- 남은 blocking finding과 각각의 상태
- 수렴하지 않는 원인 — 같은 원인이 반복되는지, 수정할 때마다 새 결함이 나오는지
- 라운드 연장이 타당한지에 대한 판단과 제안 라운드 수

비차단 P0·P1은 임계값을 막지 않지만, merge 전 확인 단계에서 반드시 사용자에게 보고하고 후속 작업으로 등록합니다.

## 7. 원장

라운드는 리뷰 대기 상태에서 세션을 넘길 수 있으므로 진행 상태를 남깁니다.

**리뷰 도구가 이미 PR에 결과를 남기고 있다면 그 코멘트가 원장입니다.** 같은 내용을 다시 만들지 마세요.

단, 코멘트 하나를 head마다 덮어쓰는(sticky) 리뷰어는 이전 라운드의 결과가 사라집니다. 그 리뷰어의 finding은 판정 기록에 ID·요지·중요도를 남겨 두어야 다음 라운드에서 해소 여부를 대조할 수 있습니다. §2.1의 `게시 위치`에 덮어쓰기 여부를 적어 두는 이유입니다.

**판정 기록의 위치.** PR이 있으면 판정 기록은 실행 주체의 세션 안에서 유지하고 라운드마다 사용자에게 보고합니다(§10). tracked 파일에 쓰면 리뷰 대상 head가 바뀌고, PR 코멘트 게시는 위임되지 않았습니다. 세션을 넘겨야 하면 마지막 §10 보고가 인계 자료이며, 다음 세션은 그 보고와 PR에 남은 리뷰어 결과로 원장을 재구성합니다. PR이 없을 때만 [TODO.md](./TODO.md) 임시 블록을 씁니다.

- **읽기:** 각 리뷰어의 결과를 head SHA로 정렬해 읽습니다. 대부분의 리뷰 도구는 코멘트에 head SHA나 라운드 번호를 남깁니다. 그것으로 라운드 경계와 §4의 정족수를 판단합니다.
- **쓰기:** 라운드마다 **판정 결과만** 별도로 남깁니다. 리뷰어가 이미 쓴 finding 본문을 복제하지 않습니다.
- PR이 없으면 [TODO.md](./TODO.md)의 해당 작업 아래 임시 블록으로 둡니다. PR이 있으면 위 「판정 기록의 위치」를 따릅니다.
- **수명:** merge 후에는 판정 기록을 압축해 [TODO.md](./TODO.md) `Completed` 항목의 검증 근거 한 줄로 남깁니다.

판정 기록에는 대상, 확정한 파라미터, 현재 라운드와 최대 라운드, 라운드별 head(base가 바뀌었다면 base도)와 결과가 도착한 리뷰어(`부분 결과`·`결과 없음` 표시 포함), `rereview = request`였다면 라운드별로 요청을 보낸 리뷰어와 접수 확인 결과, 검증 결과를 남기고 finding은 다음 형식으로 정리합니다.

| ID | 라운드 | head | 리뷰어 | 중요도 | confidence | blocking | 판정 | 근거 | 처리 | commit |
|---|---|---|---|---|---|---|---|---|---|---|
| F-001 | 1 | `abc123` | A, B | P1 | 0.9 | true | 유효 | 근거 | 수정 | SHA |

`리뷰어` 열에는 같은 finding을 보고한 리뷰어를 모두 적고, 중요도가 서로 달랐다면 각각의 값도 남깁니다.

## 8. 조기 중단

라운드 예산이 남아 있어도 다음 경우에는 중단하고 지시를 기다립니다.

- 같은 모듈에서 라운드마다 새 blocking P0·P1이 발생하는 경우 — 개별 결함이 아니라 설계 문제 신호입니다
- 수정이 [PLAN.md](./PLAN.md)의 확정된 결정과 충돌하는 경우
- 수정에 요청 범위를 넘는 광범위한 리팩터링이 필요한 경우
- 검증 명령을 실행할 수 없어 수정의 안전성을 확인할 수 없는 경우
- 상시 리뷰어가 라운드마다 타임아웃되는 경우 — 개별 결함이 아니라 리뷰 파이프라인 장애 신호입니다
- 같은 리뷰어가 라운드마다 `부분 결과`를 내는 경우 — PR이 리뷰어의 처리 한도를 넘었다는 신호입니다. 분할을 제안합니다

## 9. 종료 후 문서 정합성

- merge한 경우에만 [TODO.md](./TODO.md) 항목을 `- [x]`로 변경하고 검증 근거를 남깁니다.
- 이관한 비차단 finding을 [TODO.md](./TODO.md) `Backlog` 또는 [REVIEW.md](./REVIEW.md) §9 Accepted Deferrals에 등록합니다.
- [PLAN.md](./PLAN.md)는 실제 결정이 바뀐 경우에만 수정합니다.

## 10. 종료 보고

라운드가 끝나면 한국어로 다음을 보고합니다.

- 진행한 라운드 수와 최종 상태 (merge / 지시 대기 / 중단)
- 라운드별 head, 결과가 도착한 리뷰어, `부분 결과`와 `결과 없음`으로 처리한 리뷰어, finding 수와 판정 결과
- 리뷰어별로 다르게 보고된 finding과 통합 결과
- 무효로 판정한 finding과 그 근거 요약
- 수행한 수정과 commit
- 실행한 검증과 그 결과, 실행하지 못한 검증과 이유
- 다음 PR로 이관한 항목
