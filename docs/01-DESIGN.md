# 변경 설계 절차

> 이 문서는 설계를 만드는 공통 절차입니다. 제품 기준은 [00-PROJECT.md](./00-PROJECT.md), 전역 작업은 [02-TODO.md](./02-TODO.md), 문서별 소유권과 브랜치 운영은 [DOCS_GUIDE.md](./DOCS_GUIDE.md)에 있습니다.

## Metadata

- **Status:** Active
- **Owner:** 프로젝트에 맞게 작성
- **Last reviewed:** YYYY-MM-DD
- **Review cadence:** 설계 절차 자체가 변경될 때

## 1. 적용 조건

다음 변경에 적용합니다.

- 구조·기술 스택·공개 계약·데이터 스키마를 변경하거나 마이그레이션이 필요함
- 합리적인 대안이 둘 이상이며 트레이드오프 판단이 필요함
- 새 기능·사용자 동작 변경의 요구가 모호하거나, 여러 세션에 걸쳐 의도와 요구사항을 보존해야 함
- 사용자가 `design` 스킬을 명시적으로 호출함

다음에는 전체 절차를 반복하지 않습니다.

- 원인이 구조 문제가 아닌 명확한 버그 수정
- 외부 계약이 바뀌지 않는 단일 모듈의 명확한 변경
- 문서·테스트·주석만 바뀌는 명확한 변경
- 이미 승인된 제품·확장 SPEC 또는 결정의 구현. 해당 요구사항과 완료 조건을 연결하고 필요한 구현 계획만 작성합니다. 요구사항·계약·완료 조건을 바꾸려면 그 변경에 이 절차를 적용합니다.

명시적 `design` 호출은 예외보다 우선합니다. 작은 요청에는 아래 최소 산출물을 사용합니다. 요청이 불명확할 때는 결정에 필요한 질문만 하며, 이미 대화에서 합의한 내용을 다시 승인받지 않습니다.

## 2. 규모와 산출물

문서의 역할을 먼저 나누고 파일 수는 작업 규모에 맞춥니다. 모든 변경에 세 파일을 만들지 않습니다.

| 변경 | 산출물 |
|---|---|
| 명확하고 작은 작업 | 전역 TODO 항목 또는 작업 보고. 설계 절차 대상이 아니면 새 설계 파일을 만들지 않음 |
| 일반적인 설계 변경 | `docs/changes/<변경-ID>/01-CHANGE.md` 한 파일에 Intent·Spec 절, 구현 계획은 전역 TODO |
| 여러 세션·구성요소·계약에 걸치는 변경 | 변경 폴더의 `01-INTENT.md`와 `02-SPEC.md`; 상세 실행 계획이 필요하면 `03-PLAN.md` |
| 승인된 제품·확장 설계의 단계 구현 | 상위 설계의 해당 절과 완료 조건을 참조. TODO 또는 변경별 PLAN만 작성하며 INTENT·SPEC을 형식상 재작성하지 않음 |

마이그레이션·공개 계약 변경·여러 PR 또는 로컬 검토 단위가 필요한 작업은 분리형을 우선 검토합니다. 파일 수만으로 안전성이나 설계 완성도를 판단하지 않습니다.

복사용 양식은 `docs/changes/_template/`에 있습니다. 이 폴더는 작업이 아니며 프로젝트 결정·진척으로 집계하지 않습니다. 필요한 파일만 새 변경-ID 폴더로 복사하고 예시를 교체합니다. `03-PLAN.md`만 필요하면 상위 SPEC을 가리키도록 바꾸고 없는 형제 파일 링크를 제거합니다.

두 형식 모두 [00-PROJECT.md](./00-PROJECT.md) §8에 결정과 정본 위치를 연결하고, [02-TODO.md](./02-TODO.md)에 변경 단위 항목을 둡니다. 설계 상세를 두 곳에 복제하지 않습니다. PLAN을 만들면 그 변경의 상세 작업·검증 상태는 PLAN에서만 관리하고 전역 TODO에는 링크와 통합 수준 정보만 남깁니다.

결정이 리뷰 판정에 영향을 주면 [REVIEW.md](./REVIEW.md) §6 Project-specific Invariants 또는 §9 Accepted Deferrals와 [.cursor/BUGBOT.md](../.cursor/BUGBOT.md)의 해당 복제본을 함께 갱신합니다. 기존 commit 권한 규칙은 그대로 적용됩니다.

## 3. 단계

### 3.1 의도 확인 — Intent

- 요청 출처, 현재 불편, 기대 결과, 대상 사용자, 범위·비범위, 제약, 미해결 질문을 적습니다.
- 사용자가 구현 방식을 지정했다면 제약으로 보존합니다. 아직 선택하지 않은 구현 방법을 요구사항으로 바꾸지 않습니다.
- [00-PROJECT.md](./00-PROJECT.md) §1~§4 및 관련 상위 설계와 대조합니다.
- 원래 대화가 없으면 기존 자료에서 확인되는 내용만 정리하고 `기존 자료에서 재구성`과 근거를 표시합니다. 과거 요청·승인·날짜를 만들어내지 않습니다.

### 3.2 요구사항과 시나리오 — Spec

- 요구사항에 식별자와 검증 가능한 조건을 붙입니다.
- 각 요구사항에 최소 하나의 상황·입력·관찰 가능한 결과를 연결합니다. 성공뿐 아니라 관련 실패·경계 조건도 다룹니다.
- 실제 코드와 계약의 호출자·소비자를 읽고, 상충하는 요구나 미해결 질문을 드러냅니다.
- 요구사항과 구현 방법을 별도 절로 구분합니다.

### 3.3 대안 비교

- 없어도 되는가 → 코드베이스에 있는가 → 표준 라이브러리 → 플랫폼 기본 기능 → 설치된 의존성 순으로 검토한 뒤 필요한 최소 변경을 제안합니다.
- 대안을 둘 이상 비교합니다. 하나뿐이면 변경하지 않음을 대안에 포함합니다.
- 변경 범위, 위험, 호환성, rollback, 새 의존성과 기각 이유를 적습니다. 새 production dependency는 사용자 동의가 필요합니다.

### 3.4 설계 — Spec

- 구성요소·책임·경계, 데이터 흐름, 공개 계약, 오류·실패 처리, 마이그레이션·배포 순서, rollback을 정리합니다.
- 요구사항별 검증 방법을 연결합니다.
- [REVIEW.md](./REVIEW.md) §6의 불변조건과 [00-PROJECT.md](./00-PROJECT.md)의 현재·목표 구조를 대조합니다.
- 상위 설계를 확장하거나 대체하는 범위를 결정 ID·절로 특정합니다. 새 문서나 큰 번호라는 이유로 상위 설계 전체를 대체하지 않습니다.

### 3.5 실행 계획 — Plan

- 변경 대상 파일·구성요소, 순서, 선행조건, 검증 방법을 적습니다.
- 작업은 하나의 PR 또는 로컬 검토 단위로 확인 가능한 크기로 나눕니다.
- 상세 작업의 정본은 전역 TODO 또는 변경별 PLAN 중 하나로 정합니다. 변경 폴더에 별도 TODO를 추가하지 않습니다.
- 병렬 작업은 변경-ID와 파일 소유 범위를 나눕니다. 같은 파일·계약을 바꾸는 작업의 통합 순서와 재검증 조건을 정합니다.

### 3.6 사용자 합의

문제·범위, 요구사항, 대안·선택 이유, 설계, 위험·rollback, 작업·검증 계획, 산출물 위치를 함께 제시합니다. **합의 전에는 구현을 시작하지 않습니다.**

기존 대화에서 승인한 범위는 재승인 없이 진행합니다. 새로 드러난 미합의 결정만 확인합니다. 승인된 설계의 단계 구현이면 상위 승인과 완료 조건을 확인하는 것으로 충분합니다. 합의된 순간 §4에 따라 기록합니다. 기록만 요청받은 제안은 `Draft` 또는 `Proposed`로 유지합니다.

## 4. 산출물과 갱신 규칙

### 식별과 승인

- 변경-ID는 안정적인 식별자이며 브랜치명·PR 번호와 별개입니다. 번호 충돌이 적은 `<UTC 날짜>-<고유 slug>` 또는 기존 이슈 ID를 사용할 수 있습니다.
- Intent·Spec은 `Draft / Accepted / Superseded / Rejected`로 승인 상태를 기록합니다. 승인한 사람, 범위, 확인 가능한 대화·문서 revision 등의 근거를 남깁니다.
- 결정 상태의 기준은 PROJECT §8이고, 문서 승인 상태는 그 문서에 적용됩니다. 승인 기록은 서로 연결합니다. 승인된 SPEC에 추가한 새 제안을 기존 승인에 포함시키지 않습니다.
- Git 작성자나 commit 존재만으로 사용자 승인을 추정하지 않습니다. 파일 작성·승인은 commit·push·merge·배포 위임이 아닙니다.

### 합본형과 분리형

`01-CHANGE.md`는 다음 절을 사용합니다. 상세 내용은 분리형 양식과 같습니다.

1. Metadata — 변경-ID, 승인 상태·근거, 상위 설계, 결정 ID, 실행 작업의 위치
2. Intent — 요청·문제·결과·범위·제약·미해결 질문
3. Spec — 요구사항·시나리오·설계·대안·호환성·검증

분리형은 [INTENT 양식](./changes/_template/01-INTENT.md), [SPEC 양식](./changes/_template/02-SPEC.md), [PLAN 양식](./changes/_template/03-PLAN.md)을 사용합니다. 합본형에서 분리형으로 전환하면 내용을 옮기고 이전 파일을 정본으로 남기지 않습니다. 참조와 승인 근거를 새 위치로 연결합니다.

### 문서 수명

- Intent는 원래 요청을 보존합니다. 요구가 바뀌면 변경 이유와 재승인 범위를 기록하며 원래 요청을 조용히 덮어쓰지 않습니다.
- Spec의 계약·완료 조건을 바꾸면 구현 전에 영향과 사용자 합의를 확인합니다. 결정 변경은 PROJECT에서 기존 결정을 `Superseded`로 남기고 새 결정에 연결합니다.
- 승인된 버전은 Git revision 또는 별도 보존본으로 식별 가능해야 합니다. 아직 commit하지 않았다면 기존 승인 내용을 보존하고 새 내용의 미합의 상태를 구분합니다. 기록을 위해 자동 commit하지 않습니다.
- Plan은 구현에 맞춰 갱신하는 문서입니다. 작업 순서·검증 결과를 유지하되, Spec의 요구나 완료 조건을 바꾸는 수단으로 사용하지 않습니다.
- 제품 기준과 장기 확장 설계는 계속 유지하는 문서입니다. 구현 시작 후 본문을 일괄 동결하지 않습니다. 개별 변경의 과거 합의 기록과 현재 제품 설명을 구분합니다.
- 변경별 체크 완료는 해당 브랜치에서의 구현·검증 완료입니다. 통합 완료·릴리스·지원 검증을 뜻하지 않습니다.
- 리뷰 라운드가 통과한 뒤에는 PLAN을 포함한 tracked 문서를 수정해 head를 바꾸지 않습니다. 판정·인계 기록은 [REVIEW_ROUND.md](./REVIEW_ROUND.md) §7·§9에 따라 다음 관련 작업으로 전달합니다.

## 5. 하지 말 것

- 작은 요청이나 승인된 단계 구현에 INTENT·SPEC·PLAN을 모두 강제하는 것
- 전역 TODO와 변경별 PLAN에 같은 상세 체크리스트·진행 상태를 복제하는 것
- 설계 승인, 브랜치 구현, 통합, 릴리스와 지원 검증을 같은 완료로 표시하는 것
- 파일 번호를 우선순위나 결정 ID로 해석하는 것
- 미합의 내용을 현재 제품이나 확정된 목표 구조로 기록하는 것
- 이 절차 문서에 프로젝트 고유 설계나 운영 현황을 쓰는 것

## 6. 기존 제품·확장 설계

- 기존 설계 문서는 기본적으로 유지하고 PROJECT의 설계 인덱스에서 연결합니다. 과거 기록을 새 INTENT처럼 꾸미거나 모든 내용을 변경 폴더로 옮기지 않습니다.
- 사용자가 통합을 요청하면 PROJECT에 기본 제품 설계를 병합할 수 있습니다. 중복 설명·작업 상태를 정리하되 결정 ID·근거·계약·검증 조건과 참조를 보존합니다.
- 장기 확장에는 선택형 [10-EXTENSION.md](./10-EXTENSION.md)를 사용하거나 기존 확장 문서를 연결합니다. 같은 설계를 두 곳에서 관리하지 않습니다.
- 확장 설계에는 적용할 상위 revision·절, 유지·대체 범위, 단계 의존성과 완료 조건을 남깁니다. 단계의 현재 작업 상태는 TODO/PLAN을 참조합니다.
- 기존 자체 체크리스트가 있으면 어느 문서가 상세 상태를 소유하는지 명시하고 다른 곳은 링크로 바꿉니다. 단계가 승인되어 있다면 그 구현은 §1의 예외를 유지합니다.

## 7. 외부 스펙 도구

외부 도구의 변경 산출물은 같은 역할의 INTENT·SPEC·PLAN을 대체할 수 있습니다. PROJECT는 결정과 정본 위치의 인덱스, 전역 TODO는 변경 단위 계획을 유지합니다. 상세 설계와 실행 상태는 지정한 도구 산출물에서만 관리합니다. 공존 규칙은 [TEMPLATE_GUIDE.md](./TEMPLATE_GUIDE.md) §4를 따릅니다.
