## 1. Intent

### 1.1 문제

현재 불편, 영향을 받는 사용자·시스템과 확인된 근거를 적습니다.

### 1.2 기대 결과

어떤 결과가 되면 문제가 해결되는지 적습니다. 아직 선택하지 않은 구현 방식과 구분합니다.

### 1.3 범위와 비범위

이번 요청에서 포함하고 제외할 것을 적습니다.

### 1.4 제약

호환성·보안·일정·운영 제약과 사용자가 명시한 구현 요구를 보존합니다.

### 1.5 미해결 질문

다음 단계 전에 답해야 하는 질문과 보류 가능한 질문을 구분합니다.

## 2. Spec

### 2.1 요구사항과 시나리오

| 요구사항 ID | 요구사항 | 상황·입력 | 관찰 가능한 결과 | 검증 방법 |
|---|---|---|---|---|
| R-001 | 예시 요구사항 | 조건 | 결과 | 검사 |

성공·실패·경계 조건과 Intent의 질문이 해결되었는지 확인합니다. `R-nnn`은 이 변경 폴더 안에서만 고유합니다.

### 2.2 대안과 선택 이유

변경하지 않음을 포함한 대안, 선택 이유, 기각 이유를 적습니다.

### 2.3 설계와 계약

구성요소, 책임, 데이터 흐름, 공개 계약, 오류 처리와 상위 불변조건을 적습니다. 요구사항과 구현 방법은 구분합니다.

### 2.4 상위 설계에 미치는 영향

유지·확장·대체하는 결정 ID·절과 이유를 적습니다. 문서 전체의 무조건적인 우선순위를 만들지 않습니다.

### 2.5 위험·호환성·rollback

호환성, 전환·배포 순서, 실패 시 복구와 검증 조건을 적습니다.

### 2.6 완료 조건과 미해결 사항

이 변경을 검증할 조건과 남은 질문을 적습니다. 구현·병합·릴리스·지원 검증 중 어떤 완료를 요구하는지 명시합니다. 실행 체크박스와 현재 상태는 실행 정본에만 둡니다.

## 3. 변경 기록

요구가 바뀌면 이유와 재승인 범위를, 계약·완료 조건이 바뀌면 대체된 결정·revision을 남깁니다. 원래 요청을 조용히 덮어쓰거나 이전 승인에 새 요구를 포함시키지 않습니다.
