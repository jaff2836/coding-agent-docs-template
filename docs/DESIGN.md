# Change Design Procedure

> 이 문서는 구현 전에 설계를 정리하는 **절차**입니다. 프로젝트의 목표와 결정은 [PLAN.md](./PLAN.md)(§2가 큰 규모로 판정한 변경의 설계 상세는 `docs/changes/` 파일), 작업 상태는 [TODO.md](./TODO.md)에 기록하며, 이 문서에는 프로젝트 정보를 쓰지 않습니다.

## Metadata

- **Status:** Active
- **Owner:** 프로젝트에 맞게 작성
- **Last reviewed:** YYYY-MM-DD
- **Review cadence:** 설계 절차 자체가 변경될 때

## 1. 적용 조건

다음 중 하나에 해당하는 변경에 적용합니다.

- 구조 변경 — 컴포넌트 경계, 모듈 분할, 데이터 흐름이 바뀜
- 기술 스택 변경 — 런타임, 프레임워크, 저장소, 주요 라이브러리 교체 또는 추가
- 공개 계약 변경 — 공개 API, CLI 인터페이스, 설정 스키마, 데이터 스키마, 파일 형식
- 마이그레이션이 필요한 변경
- 합리적인 대안이 둘 이상 있고 트레이드오프가 있는 변경
- 사용자가 `design` 스킬을 명시적으로 호출한 경우

다음에는 적용하지 않습니다. 보통 방식으로 구현합니다.

- 버그 수정. 원인이 구조 문제라서 위 조건에 걸리면 그때 적용합니다
- 이미 확정으로 기록된 설계의 구현 — [PLAN.md](./PLAN.md) §8의 `Accepted` 결정, 또는 §6에서 말하는 기존 설계 문서의 확정 단계. 그 완료 조건을 그대로 따르는 구현이라면 설계는 이미 끝난 것입니다. 완료 조건을 바꿔야 한다면 그 변경이 이 절차의 대상입니다
- 단일 모듈 안에서 끝나고 외부 계약이 바뀌지 않는 변경
- 문서, 테스트, 주석만 바뀌는 변경

사용자가 `design` 스킬을 명시적으로 호출한 경우에는 위 예외보다 호출이 우선합니다. 예외에 해당해도 절차를 적용하고, 규모가 작으면 §2의 중간 규모로 진행합니다.

판단이 애매하면 한 문장으로 사용자에게 묻습니다. 절차를 적용하는 데 사용자 동의가 필요하지는 않지만, 사용자가 "그냥 고쳐 달라"고 한 요청을 이 절차로 확장하지 마세요.

## 2. 규모와 산출물

적용 대상이면 규모를 먼저 정합니다. 규모가 산출물의 위치를 정합니다.

**중간 규모** — 한두 개 PR로 끝나고 컴포넌트 두 개 이하를 건드립니다.

- 산출물: [PLAN.md](./PLAN.md) §8 Decisions 행 하나 + [TODO.md](./TODO.md) 작업. 설계 내용은 결정 행의 Rationale·Alternatives·Consequences에 담습니다.

**큰 규모** — 다음 중 하나 이상: 컴포넌트 세 개 이상, 마이그레이션 또는 공개 계약 변경, PR 세 개 이상으로 나뉨, 병행 운영이나 단계적 rollout이 필요.

- 산출물: `docs/changes/<날짜>-<slug>.md` 파일 하나(§4 형식) + [PLAN.md](./PLAN.md) §8 Decisions 행(파일 링크와 한 줄 요약) + [TODO.md](./TODO.md) 작업들(각각 파일의 작업 ID 참조).

**두 규모 공통** — 결정이 리뷰 판정에 영향을 주면(새 불변조건, 리뷰어가 되돌리라고 요구할 수 있는 선택, 잔여 간극의 수용) 규모와 무관하게 [REVIEW.md](./REVIEW.md) §6 Project-specific Invariants 또는 §9 Accepted Deferrals와 [.cursor/BUGBOT.md](../.cursor/BUGBOT.md)의 복제본을 같은 커밋에서 갱신합니다. 빠뜨리면 이후 리뷰가 canonical 정책에 없는 이전 기준을 계속 적용합니다.

두 경우 모두 결정 이유의 canonical 위치는 [PLAN.md](./PLAN.md)이고, 작업 상태의 canonical 위치는 [TODO.md](./TODO.md)입니다. 큰 규모의 설계 파일은 상세를 담되, 결정 상태나 작업 진행 상태를 그 파일에서 따로 관리하지 않습니다.

## 3. 단계

여섯 단계를 순서대로 진행합니다. **6단계에서 사용자와 합의하기 전에는 코드를 변경하지 않습니다.**

### 3.1 문제 정의

- 현재 동작, 원하는 동작, 이번 범위에서 다루지 않는 것을 각각 한두 문장으로 적습니다.
- [PLAN.md](./PLAN.md) §1~§4(Context, Goals, Non-goals, Constraints)를 읽고 충돌하는 목표나 제약이 있으면 여기서 드러냅니다.
- 관련 코드를 실제로 읽고 호출 흐름을 끝까지 따라갑니다. 읽지 않은 코드에 대해 설계하지 않습니다.

### 3.2 요구사항과 시나리오

- 요구사항은 검증 가능한 문장으로 씁니다. "빠르게"가 아니라 "p95 200ms 이하".
- 각 요구사항에 최소 하나의 시나리오를 붙입니다. 형식은 다음과 같습니다.

  ```text
  요구사항: 시스템은 <조건>에서 <동작>해야 한다.
    시나리오: <상황>일 때
      WHEN <입력 또는 사건>
      THEN <관찰 가능한 결과>
  ```

- 요구사항끼리 충돌하거나, 어느 요구사항도 다루지 않는 입력·상태가 있는지 점검합니다. 빈틈은 3.1로 돌아가 사용자에게 묻습니다.
- 요구사항에 구현 방법을 쓰지 않습니다. 방법은 3.4의 몫입니다.

### 3.3 대안 비교

- 대안을 둘 이상 놓습니다. 하나뿐이라면 "변경하지 않음"이 두 번째 대안입니다.
- 첫 대안을 만들기 전에 [AGENTS.md](../AGENTS.md) Change Rules의 재사용 순서를 그대로 적용합니다 — 없어도 되는가, 코드베이스에 이미 있는가, 표준 라이브러리가 하는가, 플랫폼 기능이 있는가, 이미 설치된 의존성이 하는가. 이 순서를 통과한 뒤에만 새 코드를 대안으로 놓습니다.
- 각 대안에 대해 적습니다: 바뀌는 범위, 위험, 호환성 영향, rollback 방법, 새 의존성 여부. 새 production dependency가 필요하면 그 대안은 사용자 동의가 있어야 선택할 수 있습니다.
- 기각한 대안과 이유를 남깁니다. 나중에 같은 논의를 반복하지 않기 위한 기록입니다.

### 3.4 설계

선택한 대안에 대해 다음을 정리합니다. 해당 없는 항목은 "해당 없음"으로 명시합니다.

- 구성요소와 책임, 그리고 서로의 경계
- 데이터 흐름 — 대표 요청이 입력부터 결과까지 이동하는 경로
- 오류 처리와 실패 시 동작
- 마이그레이션 순서와 병행 운영 조건
- 테스트 전략 — 3.2의 시나리오가 어느 테스트로 검증되는지
- [REVIEW.md](./REVIEW.md) §6 Project-specific Invariants를 하나씩 대조해 위반하지 않음을 확인
- [PLAN.md](./PLAN.md) §5 Current Architecture·§6 Target Architecture와의 정합 — 목표 구조를 바꾸는 설계라면 그 사실을 명시. 조건부 절을 삭제한 저장소는 현재 구조를 설명하는 문서(§6의 기존 설계 문서 등)와 대조

### 3.5 작업 분해

- [TODO.md](./TODO.md)의 작업 형식(`T-xxx`, 범위·완료 조건·검증·관련 결정)으로 나눕니다.
- 각 작업은 PR 하나 이하로 끝나야 합니다. 리뷰어가 한 번에 읽을 수 없는 크기는 나눕니다.
- 작업 순서와 의존성을 적습니다. 마이그레이션이 있으면 "배포 순서"가 작업 순서를 결정합니다.
- 각 작업의 검증에 3.2의 시나리오 중 어느 것이 대응되는지 적습니다.

### 3.6 사용자 합의

다음을 한 번에 제시하고 사용자 판단을 받습니다.

1. 문제와 범위 (3.1)
2. 선택한 대안과 이유, 기각한 대안과 이유 (3.3)
3. 설계 요약과 확인한 불변조건 (3.4)
4. 위험과 rollback (3.3, 3.4)
5. 작업 목록과 순서 (3.5)
6. 규모 판정과 산출물 위치 (§2)

사용자가 합의하면 산출물을 기록하고(§4) 구현을 시작합니다. 수정 요청이 오면 해당 단계로 돌아갑니다. 합의 없이 "임시로" 구현을 시작하지 않습니다.

## 4. 산출물 기록 규칙

**PLAN.md §8 Decisions 행**

- 합의 전에는 기록하지 않습니다. 합의된 순간 `Accepted`로 기록합니다. 사용자가 "기록만 하고 보류"를 원하면 `Proposed`로 기록하고 §11 Open Questions에 남은 질문을 적습니다.
- 큰 규모는 Decision 열에 설계 파일 링크와 한 줄 요약을 씁니다.
- 기존 결정을 대체하면 기존 행을 `Superseded`로 바꾸고 새 행에서 참조합니다. 기존 행을 지우지 않습니다.

**TODO.md 작업**

- 3.5의 작업을 `Next`(또는 첫 작업은 `In Progress`)에 추가합니다. 관련 결정 항목에 Decisions ID를 씁니다.

**`docs/changes/<날짜>-<slug>.md`** (큰 규모만, 예: `docs/changes/2026-09-04-split-gateway.md`)

```markdown
# <변경 제목>

- **Decision:** D-xxx
- **Status:** `Active`, 또는 대체되었으면 `Superseded by <새 파일 링크>`. 그 외의 진행 상태는 이 파일이 관리하지 않습니다 — PLAN.md D-xxx와 TODO.md를 보세요.

## 1. 문제와 범위
## 2. 요구사항과 시나리오
## 3. 대안과 선택 이유
## 4. 설계
## 5. 위험과 rollback
## 6. 작업 (TODO.md T-xxx 목록과 순서)
```

- 날짜는 UTC 기준 합의일을 연-월-일 순서로 적습니다.
- 구현이 시작된 뒤에는 이 파일의 본문(§1~§6)을 고치지 않습니다. 설계가 바뀌면 새 파일을 만들고, PLAN.md §8의 기존 결정을 `Superseded`로 바꾸며, 기존 파일은 머리의 `Status` 줄만 `Superseded by <새 파일 링크>`로 바꿉니다. 본문은 "그때 왜 그렇게 결정했는가"의 기록으로 남깁니다.
- 구현이 끝나면 PLAN.md §5 Current Architecture를 갱신합니다. 설계 파일이 현재 구조의 설명을 대신하지 않습니다.

## 5. 하지 말 것

- 합의 전에 구현을 시작하는 것. 탐색용 코드를 썼다면 합의 전에 되돌립니다
- 설계 파일만 만들고 PLAN.md·TODO.md를 갱신하지 않는 것. 두 문서를 읽는 사람은 설계 파일의 존재를 모릅니다
- 합의되지 않은 설계를 PLAN.md §6 Target Architecture에 넣는 것. 그 표는 합의된 것만 담습니다
- 요구사항에 구현 세부를 쓰는 것. 나중에 구현이 바뀌면 요구사항도 틀린 것처럼 보입니다
- 사용자의 작은 요청을 이 절차로 확장하는 것. §1의 조건을 충족하지 않으면 적용하지 않습니다
- 이 문서에 프로젝트 고유 정보를 쓰는 것. 이 문서는 절차이며, 프로젝트마다 다른 내용은 PLAN.md에 갑니다

## 6. 기존 설계 문서가 있는 저장소

이 절차를 도입하기 전부터 큰 설계 문서(제품 전체 설계, 다단계 확장 계획 등)를 가진 저장소가 있습니다. 그 문서는 다음처럼 다룹니다.

- **옮기지도, §4 형식으로 바꾸지도 않습니다.** 그 문서는 변경 하나의 합의 기록이 아니라 계속 갱신되는 제품 설계이며, 대개 자체 단계 체크리스트·risk register·용어 정의를 담습니다. `docs/changes/`로 옮기면 §4의 "구현 시작 후 수정하지 않음" 규칙과 즉시 충돌하고, 그 문서를 가리키는 링크만 깨집니다. 이 절차는 도입 이후의 **새 변경**에만 적용합니다.
- **[PLAN.md](./PLAN.md)가 인덱스인 저장소**에서는 결정 본문이 PLAN.md가 아니라 기존 설계 문서에 있습니다. 이 경우 §2의 중간 규모 산출물 "PLAN.md §8 Decisions 행"은 "결정 본문(기존 설계 문서의 해당 절) + PLAN.md §8 인덱스 행"으로 읽습니다. 큰 규모의 `docs/changes/` 파일은 그대로입니다.
- 기존 문서가 **자체 단계 체크리스트**를 가지면, 그 단계의 구현은 §1의 제외 조건에 해당합니다. 단계별 구현 여부의 인덱스는 [PLAN.md](./PLAN.md), 열린 실행 작업은 [TODO.md](./TODO.md)가 기준이며, 체크리스트 상태를 설계 문서와 TODO.md 두 곳에서 관리하지 않습니다.
- 적용 저장소의 이 문서에는 기존 설계 문서의 **경로만** 한 줄로 덧붙이세요. 결정 내용은 여기 적지 않습니다.

## 7. 외부 스펙 도구를 쓰는 저장소

OpenSpec처럼 변경 단위 산출물을 자기 디렉터리에 만드는 도구를 쓰는 저장소는, §2의 `docs/changes/` 파일을 그 도구의 산출물로 대체할 수 있습니다. 그 경우에도 결정 이유는 [PLAN.md](./PLAN.md), 작업 상태는 [TODO.md](./TODO.md)가 canonical이며, 도구 산출물에는 PLAN.md 결정 ID를 남깁니다. 공존 규칙은 [Template Guide](./TEMPLATE_GUIDE.md) §4 「외부 방법론·행동 규칙 도구」에 있습니다.
