안정 토큰은 `scope=explicit-whole-project`, `mode=read-only`, `evidence_status=verified|inference|unverified`입니다.

이 스킬은 사용자가 프로젝트 전체 분석, 기술 실사, 아키텍처 평가 또는 도입 타당성 평가를 명시적으로 요청했을 때만 적용합니다. 일반적인 기능 구현, 버그 수정, 질문 답변 또는 PR 리뷰에는 이 절차 전체를 적용하지 않습니다.

## 1. 목적

분석의 목적은 저장소의 실제 코드와 설정을 근거로 다음 질문에 답하는 것입니다.

- 이 프로젝트는 어떤 문제를 누구를 위해 해결하는가?
- 현재 구현된 기능과 문서상 목표는 무엇이 다른가?
- 어떤 기술과 구조로 동작하며 핵심 데이터는 어떻게 흐르는가?
- 로컬 실행, 테스트, 배포 및 운영에 무엇이 필요한가?
- 정확성, 보안, 성능, 유지보수성 측면의 주요 위험은 무엇인가?
- 지금 도입하거나 확장해도 되는가? 그렇지 않다면 무엇을 먼저 보완해야 하는가?

분석은 코드 작성이나 리팩터링 작업이 아닙니다. 사용자가 명시적으로 요청하지 않은 파일 수정, 의존성 설치, 마이그레이션, 배포, 외부 서비스 호출 또는 문서 상태 변경을 수행하지 않습니다.

## 2. 분석 원칙

### 2.1 근거 우선

- 저장소의 실제 코드, 설정, 테스트, CI 및 배포 파일을 1차 근거로 사용합니다.
- README와 계획 문서는 의도와 운영 절차를 설명하는 자료로 사용하되, 실제 코드와 일치하는지 별도로 확인합니다.
- 중요한 판단에는 가능한 한 저장소 상대 경로와 관련 심볼, 설정 키 또는 섹션을 제시합니다.
- 확인하지 못한 내용을 사실처럼 단정하지 않습니다.

### 2.2 사실, 추론, 미확인의 구분

분석 결과는 다음 기준으로 구분합니다.

- **확인됨:** 코드나 설정에서 직접 확인한 사실
- **추론:** 여러 근거로부터 합리적으로 도출했지만 실행으로 검증하지 않은 판단
- **미확인:** 필요한 파일, 환경, 자격 증명 또는 실행 결과가 없어 확인할 수 없는 사항

### 2.3 사용자 요청 우선

- 사용자가 지정한 분석 범위, 제외 대상 및 출력 형식이 이 문서보다 우선합니다.
- 사용자가 특정 모듈만 요청했다면 저장소 전체를 불필요하게 분석하지 않습니다.
- [02-TODO.md](../../../docs/02-TODO.md)의 항목은 사용자 요청을 자동으로 확장하는 권한이 아닙니다.

### 2.4 안전한 분석

- 기본 분석은 읽기 전용으로 수행합니다.
- 비밀값은 출력하지 않습니다. 환경변수 이름과 요구 여부만 기록합니다.
- 기존 의존성이 준비되어 있고 외부 상태를 변경하지 않는 경우에만 관련 테스트, 타입 검사 또는 린트를 실행할 수 있습니다.
- 의존성 설치, 데이터베이스 마이그레이션, 장시간 서비스 실행 또는 외부 인프라 접근이 필요하면 실행하지 말고 필요 조건으로 기록합니다.
- 테스트를 실행하지 못했다면 그 이유와 검증 범위의 한계를 명시합니다.

## 3. 근거의 우선순위

충돌하는 정보가 있으면 다음 순서로 판단합니다.

1. 현재 코드와 실제 설정
2. 자동화된 테스트 및 CI 구성
3. 스키마, API 명세, 마이그레이션 및 배포 구성
4. [00-PROJECT.md](../../../docs/00-PROJECT.md), 연결된 제품·확장 설계, 승인된 INTENT·SPEC 및 ADR
5. README, 운영 문서, 예제 및 주석
6. [02-TODO.md](../../../docs/02-TODO.md), 변경별 PLAN과 기타 계획성 체크리스트

하위 우선순위 문서가 상위 근거와 다르면 문서-코드 불일치로 기록합니다. 단, 코드가 문서의 의도를 위반한 것인지 문서가 오래된 것인지는 별도로 판단합니다.

## 4. 분석 범위 확정

분석을 시작할 때 다음 범위를 내부적으로 확정합니다.

- 저장소 전체인지 특정 서비스·패키지·디렉터리인지
- 현재 상태 분석인지 특정 브랜치·커밋·릴리스 비교인지
- 아키텍처, 보안, 운영, 도입 검토 중 어떤 관점이 중요한지
- 실행 검증이 필요한지, 정적 분석만 필요한지
- 결과의 독자가 개발자, 관리자, 보안 담당자 또는 도입 의사결정자인지

범위가 명확하지 않더라도 안전하고 합리적인 기본값으로 분석을 진행합니다. 결과가 크게 달라지는 필수 정보가 없을 때만 사용자에게 질문합니다.

## 5. 분석 절차

### 5.1 저장소 기준점 확인

다음을 먼저 확인합니다.

- 저장소 루트와 주요 하위 프로젝트
- 현재 브랜치 또는 분석 대상 상태
- 작업 트리의 기존 변경 여부
- [AGENTS.md](../../../AGENTS.md) 및 하위 디렉터리 지침
- [00-PROJECT.md](../../../docs/00-PROJECT.md), [02-TODO.md](../../../docs/02-TODO.md), 연결된 제품·확장 설계와 실제 변경별 INTENT·SPEC·PLAN, ADR
- README, 라이선스, 기여 가이드 및 보안 정책

기존 사용자 변경은 분석 대상과 구분하며 수정하거나 되돌리지 않습니다. `changes/_template/`의 복사용 양식은 실제 설계나 진행 중인 작업으로 집계하지 않습니다.

### 5.2 프로젝트 인벤토리 작성

다음 파일을 우선 탐색해 기술 구성을 파악합니다.

- 패키지 및 의존성 선언 파일
- lockfile과 워크스페이스 설정
- 빌드, 테스트, 린트 및 타입 검사 설정
- 컨테이너, IaC, CI/CD 및 릴리스 설정
- 애플리케이션 진입점과 주요 라이브러리 진입점
- 환경변수 예제와 구성 스키마
- 데이터베이스 스키마와 마이그레이션
- API 명세, 이벤트 스키마 및 프로토콜 정의

생성물, 캐시, vendored 코드, lockfile 전체 내용처럼 분석 가치가 낮은 영역은 필요할 때만 상세히 읽습니다.

### 5.3 제품 목적과 기능 확인

문서의 설명만 반복하지 말고 실제 진입점, 라우트, 명령, 공개 API 및 주요 UI 흐름에서 구현 여부를 확인합니다.

다음을 정리합니다.

- 해결하려는 문제와 주요 사용 사례
- 대상 사용자와 운영 주체
- 구현된 핵심 기능
- 문서에는 있으나 구현 근거가 부족한 기능
- 실험적 기능, 플래그 뒤 기능 및 미완성 경로
- 명시적으로 지원하지 않는 범위

### 5.4 기술 스택과 실행 모델 분석

다음을 확인합니다.

- 언어, 런타임, 프레임워크 및 핵심 라이브러리
- 최소 또는 고정 버전과 호환성 범위
- 패키지 관리자와 빌드 시스템
- 단일 애플리케이션, 모놀리스, 모듈러 모놀리스, 서비스 분리 또는 라이브러리 구조
- 동기·비동기 실행 모델과 백그라운드 작업
- 프로세스, 스레드, 큐, 스케줄러 및 외부 서비스 경계
- 저장소, 캐시, 메시지 브로커 및 파일 시스템 사용

단순히 기술 이름을 나열하지 말고 각 기술이 어떤 책임에 사용되는지 설명합니다.

### 5.5 아키텍처와 데이터 흐름 추적

대표적인 사용자 또는 시스템 흐름을 최소 한 개 이상 선택해 끝까지 추적합니다.

예시:

1. 입력이 어디에서 들어오는가?
2. 어디에서 인증·검증·정규화되는가?
3. 어떤 계층과 모듈을 통과하는가?
4. 상태는 어디에 저장되거나 캐시되는가?
5. 외부 시스템과 어떤 계약으로 통신하는가?
6. 성공, 실패, 재시도 및 취소 결과는 어떻게 반환되는가?

다음 구조적 특성을 확인합니다.

- 계층과 모듈의 책임 분리
- 의존성 방향과 순환 의존성
- 도메인 로직과 프레임워크 코드의 결합도
- 공용 인터페이스와 내부 구현 경계
- 중복 구현과 사실상의 단일 실패 지점
- 확장 지점, 플러그인 또는 어댑터 구조

관계가 복잡할 때만 간단한 Mermaid 다이어그램이나 디렉터리 트리를 사용합니다. 코드에서 확인하지 못한 관계를 다이어그램에 추가하지 않습니다.

### 5.6 코드 품질과 설계 평가

다음 관점에서 대표 모듈과 위험도가 높은 모듈을 확인합니다.

- 이름과 책임의 명확성
- 함수와 모듈의 크기 및 응집도
- 중복 로직과 변경 전파 범위
- 오류의 분류, 전달, 복구 및 로깅
- 입력 검증과 null·empty·false·zero 처리
- 상태 관리, 동시성, 트랜잭션 및 멱등성
- 자원 수명과 정리 경로
- 구성 기본값과 우선순위
- 공개 API의 안정성과 하위 호환성
- 사용된 아키텍처·디자인 패턴 및 실제 일관성

스타일 취향보다 장애 가능성과 변경 비용에 영향을 주는 구조적 문제를 우선합니다.

### 5.7 테스트와 품질 게이트 평가

다음을 확인합니다.

- 단위, 통합, 계약, E2E 및 회귀 테스트의 존재와 역할
- 핵심 성공 경로와 실패 경로의 커버 여부
- 테스트 격리, 결정성 및 외부 의존성
- fixture, mock 및 테스트 데이터의 현실성
- CI에서 실제로 실행되는 검사
- 실패가 무시되거나 조건 때문에 실행되지 않는 단계
- 로컬 명령과 CI 명령의 일치 여부
- 커버리지 수치가 있다면 그 의미와 한계

테스트가 없다는 이유만으로 결함이라고 단정하지 않습니다. 위험한 동작에 검증 수단이 없다는 점과 그 영향을 구체적으로 설명합니다.

### 5.8 보안과 신뢰 경계 평가

다음을 우선 확인합니다.

- 인증과 인가의 적용 위치
- 사용자·외부 입력의 검증과 인코딩
- 명령, SQL, 템플릿, 경로, URL 및 프롬프트 주입 가능성
- 파일 접근과 경로 순회
- SSRF 및 외부 요청 제한
- 비밀값 저장, 전달, 로그 및 빌드 산출물 노출
- 역직렬화와 업로드 처리
- 세션, 토큰, 쿠키 및 CORS 설정
- 의존성 및 공급망 신뢰 경계
- CI 워크플로 권한과 외부 Action 고정 방식
- 모델 또는 자동화 출력이 권한 있는 작업으로 이어질 때의 검증

공격 경로와 영향이 확인되지 않은 가정은 보안 취약점으로 단정하지 않고 미확인 위험으로 분류합니다.

### 5.9 성능과 확장성 평가

다음을 확인합니다.

- 요청 또는 작업당 시간·공간 복잡도
- 반복 I/O, N+1 쿼리 및 불필요한 직렬 실행
- 대용량 입력, pagination, batch 및 backpressure
- 캐시 키, 무효화 및 일관성
- connection pool, queue, worker 및 rate limit
- timeout, retry, exponential backoff 및 중복 실행
- 메모리 누수, 무제한 collection 및 로그 증가

벤치마크나 운영 지표가 없다면 성능 문제를 확정적으로 표현하지 않습니다. 코드에서 확인되는 병목 후보와 검증 방법을 구분해 제시합니다.

### 5.10 실행과 배포 준비도 평가

다음을 확인합니다.

- 요구되는 런타임, 도구 및 외부 서비스
- 필수·선택 환경변수와 기본값
- 개발, 테스트, staging 및 production 구성 차이
- 초기화, seed, migration 및 rollback 절차
- health check, readiness, graceful shutdown
- 로그, 메트릭, tracing 및 alerting
- 백업, 복구 및 장애 대응 절차
- 컨테이너 이미지, 배포 산출물 및 포함되어야 할 파일
- 운영 권한과 네트워크 요구사항

실제 운영 절차가 문서화되지 않았거나 자동화와 다르면 명시합니다.

### 5.11 문서와 코드의 정합성 확인

[00-PROJECT.md](../../../docs/00-PROJECT.md), 연결된 제품·확장 설계와 승인된 변경 명세, [02-TODO.md](../../../docs/02-TODO.md) 및 상세 실행 상태를 소유하는 변경별 PLAN이 있으면 다음을 비교합니다.

- 목표와 현재 구현
- 결정된 아키텍처와 실제 의존성 구조
- 완료 표시된 항목과 코드·테스트 근거, 그 근거가 적용되는 revision 또는 작업 트리
- 브랜치 구현·검증 완료와 지정 대상에 대한 통합·릴리스·지원 검증 완료의 구분
- 전역 TODO와 변경별 PLAN 사이의 상세 작업·검증 상태 중복 여부
- 계획 중인 항목과 이미 배포된 구현
- 폐기·보류된 설계가 현재 작업처럼 남아 있는지
- 실행·배포 문서와 실제 명령 및 설정

문서가 없으면 분석 결과에서 초안을 제안할 수 있지만, 사용자가 요청하지 않았다면 파일을 생성하지 않습니다.

### 5.12 위험과 기술 부채 우선순위화

각 위험은 다음 정보를 포함합니다.

- 중요도: Critical, High, Medium, Low
- 상태: 확인됨, 추론, 미확인
- 근거: 파일, 심볼, 설정 또는 실행 결과
- 발생 조건
- 영향
- 권장 조치
- 조치 시점: 즉시, 도입 전, 다음 릴리스, 장기 개선

같은 원인에서 파생된 증상은 중복 항목으로 늘리지 않습니다.

### 5.13 도입 판단

다음 중 하나로 결론을 제시합니다.

- **GO:** 현재 목적에 도입 가능하며 중대한 선행 조건이 없음
- **CONDITIONAL GO:** 명시한 선행 조건을 충족하면 도입 가능
- **NO-GO:** 현재 상태로는 도입 위험이 크며 구조적 보완이 필요
- **INSUFFICIENT EVIDENCE:** 핵심 근거가 없어 판단을 보류해야 함

결론에는 반드시 다음을 포함합니다.

- 판단 근거
- 적용 가능한 사용 범위
- 도입 전 필수 조치
- 감수 가능한 잔여 위험
- 재평가 조건

## 6. 대규모 저장소 분석 규칙

모든 파일을 동일한 깊이로 읽으려 하지 않습니다. 다음 순서로 깊이를 배분합니다.

1. 진입점, 인증·권한, 데이터 저장, 외부 통신
2. 핵심 도메인 로직과 공개 API
3. 빌드·배포·CI 및 마이그레이션
4. 테스트와 공용 라이브러리
5. 예제, 보조 스크립트 및 생성물

대표 파일만 표본으로 읽었다면 표본 기준과 미검토 영역을 명시합니다. 저장소가 크다는 이유로 전체를 분석했다고 표현하지 않습니다.

## 7. 권장 출력 형식

최종 결과는 한국어로 작성하며 다음 순서를 사용합니다.

### 1. 종합 요약

- 프로젝트 목적과 현재 완성도
- 가장 중요한 강점
- 가장 중요한 위험
- 최종 도입 판단

### 2. 분석 범위와 검증 수준

- 확인한 영역
- 실행한 검사
- 실행하지 못한 검사와 이유
- 표본 분석 또는 제외 영역

### 3. 프로젝트 개요와 핵심 기능

- 문제, 사용자, 주요 사용 사례
- 구현됨·부분 구현·계획 상태의 구분

### 4. 기술 스택과 실행 구조

- 기술, 버전, 역할
- 빌드·실행·배포 방식

### 5. 아키텍처와 데이터 흐름

- 주요 컴포넌트와 책임
- 대표 흐름
- 외부 시스템 및 신뢰 경계

### 6. 코드 품질과 설계

- 강점
- 구조적 문제
- 주요 패턴과 일관성

### 7. 테스트, CI/CD 및 운영 준비도

- 품질 게이트
- 배포 및 복구 가능성
- 관측 가능성

### 8. 보안과 성능

- 확인된 위험
- 추가 검증이 필요한 위험

### 9. 위험 목록

중요도, 상태, 근거, 영향, 권장 조치를 표로 정리합니다.

### 10. 문서-코드 정합성

- [00-PROJECT.md](../../../docs/00-PROJECT.md) 비교
- [02-TODO.md](../../../docs/02-TODO.md) 비교
- README 및 운영 문서 비교

### 11. GO/NO-GO 판단

- 결론
- 선행 조건
- 잔여 위험

### 12. 권장 다음 작업

- 즉시 필요한 작업
- 단기 작업
- 장기 개선
- 필요할 경우 [00-PROJECT.md](../../../docs/00-PROJECT.md)와 [02-TODO.md](../../../docs/02-TODO.md) 초안 제안

## 8. 완료 조건

다음 조건을 충족하면 분석을 종료합니다.

- 프로젝트 목적과 주요 사용자를 설명할 수 있음
- 실행 경로 또는 주요 데이터 흐름을 하나 이상 추적했음
- 핵심 기술과 각 기술의 역할을 확인했음
- 테스트·CI·배포 구성을 확인했음
- 보안·정확성·운영 위험을 근거와 함께 우선순위화했음
- 문서와 코드의 주요 불일치를 확인했음
- 검증하지 못한 영역을 명시했음
- 도입 판단과 선행 조건을 제시했음

추가 탐색이 결론이나 위험 우선순위를 바꾸지 않는다면 분석을 끝내고 결과를 작성합니다.
