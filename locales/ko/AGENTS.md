### [`docs/00-PROJECT.md`](./docs/00-PROJECT.md) — 맥락과 의사결정

- 사용자와 결정이 합의되었거나 실제 구현·지원 범위가 바뀐 경우에만 업데이트하세요. 기본 제품 설계와 기존 설계 인덱스를 함께 유지하고 상세 작업 상태는 복제하지 마세요.
- 폐기, 보류 및 제안 상태를 현재 결정과 구분하세요.

### [`docs/01-DESIGN.md`](./docs/01-DESIGN.md) — 변경 설계 절차

- 구조·기술 스택·공개 계약·데이터 스키마·마이그레이션·트레이드오프가 있는 변경, 또는 요구가 모호하거나 여러 세션에 걸쳐 의도를 보존해야 하는 기능 변경에서 구현 전에 읽고 적용하세요.
- 원인이 구조 문제가 아닌 버그 수정, 외부 계약이 바뀌지 않는 단일 모듈 안의 변경, 이미 `Accepted`된 설계의 구현에는 적용하지 마세요. 사용자의 작은 요청을 이 절차로 확장하지 마세요.
- 산출물은 규모에 맞춘 변경별 INTENT·SPEC(또는 합본형 문서), 필요한 PLAN, PROJECT §8 결정 인덱스와 전역 TODO 항목입니다. 승인된 단계 구현에는 상위 설계를 참조하고 실행 계획만 보완합니다. 사용자와 합의하기 전에는 코드를 변경하지 않으며, 기존 대화에서 승인한 범위는 재승인 없이 진행합니다.

### [`docs/02-TODO.md`](./docs/02-TODO.md) — 실행 상태

- 프로젝트 전체의 변경·마일스톤·우선순위·의존성을 관리합니다. 변경별 PLAN이 있으면 상세 체크리스트·검증 상태는 PLAN이 소유하며 전역 TODO는 링크와 통합 수준 정보만 유지합니다. PLAN이 없는 작은 작업은 TODO 항목에서 상세를 관리합니다.
- 사용자의 요청이 추적 중인 작업과 관련될 때만 읽고 업데이트하세요.
- 실제 구현과 필요한 검증을 확인해야 체크를 완료할 수 있습니다. 변경별 PLAN의 완료는 해당 브랜치의 구현·검증이며, 전역 완료는 지정한 통합 대상에 반영됐는지도 확인합니다. 로컬 Git 작업은 기준 revision과 작업 트리 범위를 기록하며 가상의 PR·merge를 만들지 않습니다.
- 범위를 실질적으로 넓히는 새 작업은 임의로 진행하지 말고 사용자에게 제안하세요.
- PR 리뷰, 분석 또는 질문 답변만 수행할 때는 수정하지 마세요.

### 제품·확장 설계와 변경 문서

- 장기 확장은 선택형 [`docs/10-EXTENSION.md`](./docs/10-EXTENSION.md) 또는 PROJECT가 연결한 기존 설계를 사용합니다. 기본 설계의 유지·확장·대체 범위를 명시합니다.
- `docs/changes/<변경-ID>/`에는 이번 변경의 의도·명세·선택적 실행 계획을 둡니다. `docs/changes/_template/`은 복사용 양식이며 실제 승인·실행 작업이 아닙니다. 모든 작업에 모든 파일을 요구하지 마세요.
- 새 세션은 현재 브랜치의 관련 변경 문서와 통합 기준을 대조합니다. 전역 TODO를 다른 브랜치의 실시간 현황으로 간주하지 마세요. 번호는 정렬용이며 승인·우선순위를 뜻하지 않습니다.
- 완료·취소된 변경 폴더는 유지하고, 현재 제품 기준은 PROJECT입니다. 전역 결정·작업 ID(`D-`/`T-`)와 변경 내부 ID를 섞지 마세요.

## Core Workflow

1. **범위 확인:** 사용자의 요청, 관련 코드 및 기존 작업 트리 상태를 확인합니다.
2. **맥락 확인:** 작업과 직접 관련된 문서와 하위 디렉터리 지침만 읽습니다.
3. **실행:** 요청 범위 안에서 가장 작은 일관된 변경을 수행합니다.
4. **검증:** 위험에 비례해 관련 테스트, 타입 검사, 린트 또는 빌드를 실행합니다.
5. **문서 정합성:** 실제 결정이나 완료 상태가 바뀐 경우에만 관련 문서를 업데이트합니다.
6. **보고:** 변경 내용, 검증 결과 및 남은 한계를 한국어로 간결하게 보고합니다.

## Change Rules

- 사용자가 만든 기존 변경과 관련 없는 파일을 보존하세요.
- 명시적인 요청 없이 commit, push, branch 삭제 또는 배포를 수행하지 마세요.
- 위 규칙의 유일한 예외는 리뷰 라운드입니다. 사용자가 라운드를 시작한 경우에 한해 해당 branch·PR 범위에서 commit, non-force push, 파라미터로 지정된 경우의 재리뷰 요청(등록된 트리거 댓글·API 호출), 처리한 finding의 리뷰 스레드 해소 표시 및 사용자 확인을 거친 merge를 위임받으며, 위임 범위는 시작 시 확정하거나 이후 사용자가 명시적으로 변경한 파라미터를 넘지 않습니다. branch 삭제, force push 및 그 외의 PR 댓글 게시는 위임되지 않습니다.
- 사용자가 제품을 명시하지 않은 채 GitHub Actions, Buildkite 등 특정 CI 설정 파일을 추가하지 마세요. 품질 게이트는 [`docs/CI.md`](./docs/CI.md)를 따릅니다.
- 새 production dependency를 추가하기 전에 필요성과 대안을 설명하고 사용자 동의를 구하세요.
- 비밀값, 토큰 및 실제 자격 증명을 코드, 로그, 문서 또는 예제에 기록하지 마세요.
- 데이터 마이그레이션과 공개 API 변경에는 호환성, 배포 순서 및 rollback 영향을 확인하세요.
- 생성 파일은 생성 원본이나 공식 생성 절차를 수정해야 하는 경우 직접 편집하지 마세요.
- 사용자가 요청하지 않은 광범위한 리팩터링으로 작업 범위를 확장하지 마세요.
- 새 코드를 쓰기 전에 순서대로 확인하세요: 없어도 되는가 → 이 코드베이스에 이미 있는가 → 표준 라이브러리가 하는가 → 플랫폼 기본 기능이 있는가 → 이미 설치된 의존성이 하는가. 그 뒤에만 필요한 최소 코드를 씁니다.
- 요청되지 않은 추상화, boilerplate, 설정 가능성을 추가하지 마세요. 삭제가 추가보다, 평범한 코드가 영리한 코드보다 낫습니다.
- 버그는 증상이 아니라 원인을 고치세요. 수정하는 함수의 호출자를 전부 확인하고, 공유 지점에서 한 번 고칩니다.
- 최소화의 대상이 아닌 것: 신뢰 경계의 입력 검증, 데이터 손실을 막는 오류 처리, 보안, 접근성, 사용자가 명시적으로 요청한 것. 자명하지 않은 로직에는 그 로직이 깨지면 실패하는 검사 하나를 남기세요.

## Code Review Rules

- 리뷰를 시작하기 전에 [`docs/REVIEW.md`](./docs/REVIEW.md)를 읽고 저장소의 canonical 리뷰 정책으로 적용하세요. 다른 adapter와 충돌하면 이 문서를 우선하세요.
- 이번 변경으로 새로 발생하거나 직접 악화된 정확성, 보안, 데이터 무결성, 호환성, 신뢰성 및 성능 결함을 우선하세요.
- 각 finding에는 중요도, `confidence`, `blocking` 값, 정확한 파일과 위치, 구체적인 발생 조건, 영향 및 수정 방향을 포함하세요.
- 확인하지 않은 추측, 개인적인 스타일 선호, 칭찬성 코멘트 및 CI가 검사하는 포맷·린트 문제를 finding으로 만들지 마세요.
- 기존 코드의 관련 없는 문제는 일반 리뷰 범위에 포함하지 마세요. 단, [docs/REVIEW.md](./docs/REVIEW.md) §3 Review Scope의 검증된 P0·P1은 `blocking=false`로 보고합니다.
- 리뷰는 기본적으로 읽기 전용입니다. 명시적인 요청 없이 코드나 프로젝트 문서를 수정하지 마세요.
